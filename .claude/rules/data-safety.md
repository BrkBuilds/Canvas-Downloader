# Data safety: JSON stores, long paths, silent failures

> Extracted from CLAUDE.md. Loads only when Claude opens a matching file.
> Each entry states the mechanism, the measurement, and why the obvious fix is wrong.

## Never destroy data on the strength of an error you have not IDENTIFIED (2026-08-06)
The failure audit found the same mistake in both of the app's stores, each time in the code written to *recover* from damage. Neither language gives you the distinction structurally, so both had to be made explicit. `tests/test_failure_hardening.py` guards all of it; all **15** mutations of the real code are caught, so re-run the mutation pass, not just the suite, after touching any of it.
- **`sqlite3.OperationalError` IS a `sqlite3.DatabaseError`**, so `except sqlite3.DatabaseError` caught *transient* failures too - and `_init_db_locked`'s handler renamed the manifest to `.canvas_sync_corrupted.db`, or **deleted** it when the rename failed. Three purely transient conditions arrive as `OperationalError` (all verified): `unable to open database file` (share offline, disk full, permissions, a malformed path), `database is locked` (another process, antivirus, a stuck WAL), `attempt to write a readonly database`. **Reproduced: a folder left with NO manifest and NO backup**, from an error whose file on disk was never damaged - attempt 0 renamed the DB aside, attempt 1 unlinked that very backup and then failed to rename again. Losing the manifest is not cosmetic: every local file becomes untracked, so the next sync re-downloads over the student's annotated copies, and `_NewVersion` protection cannot fire because it reads manifest rows.
  - **Corruption must now be PROVEN, by message whitelist** (`_is_db_corruption`: "file is not a database", "database disk image is malformed", "integrity check failed", …). An unrecognised error is treated as transient **on purpose** - the cost is asymmetric: a transient error misread as corruption destroys the sync record, while corruption misread as transient only shows an error and asks the user to retry. Transient → bounded retry → `_db_init_failed = True`, file untouched.
  - **The delete-on-rename-failure fallback is gone.** A corrupt manifest can still be salvaged by hand; a deleted one cannot. Backups are never overwritten either - the FIRST one is the copy closest to the last good sync, so new ones take `.canvas_sync_corrupted_2.db` and up.
  - `mkdir` sits above the `try:` and raised straight out of `SyncManager.__init__` (a raw traceback on the sync page); it is now flagged the same way.
- **`UnicodeDecodeError` is a SIBLING of `json.JSONDecodeError`, not a subclass** (both are `ValueError`). `except (json.JSONDecodeError, OSError)` therefore let it escape and **crash the sync page outright** - one editor re-saving a config file in a Danish ANSI codepage is enough, and these files are full of `æøå`.
- **"Unreadable" is not "empty", and `load → mutate → save` turns the second into permanent loss.** `core/library.py:_update` and `shared/helpers.py:atomic_update_sync_pairs` both degraded a failed read to `[]`/default and then WROTE, replacing every saved pair, group, name and daily-sync membership with whatever that one call happened to add. Now split by cause: **damaged content** is quarantined to `*.corrupt.json` first (the `core.preset_manager` pattern, so the data survives on disk); a **transient `OSError`** aborts the write entirely (`_READ_FAILED`), because there is nothing wrong with the file. `library._save` also reports failure instead of swallowing it - a full disk made every rename appear to work and silently revert.

## `\\?\` disables path parsing, so what you hand it must already be canonical
`shared/helpers.make_long_path` was emitting two shapes the kernel rejects (both measured 2026-08-06, both reachable from the UI):
- **UNC**: `\\server\share\f` became `\\?\\\server\share\f` → **WinError 123** ("syntax is incorrect") on *every* open, stat and sqlite connect. The correct form is `\\?\UNC\server\share\f`. Diagnostic worth reusing: assert on the error **KIND** against a non-existent host - malformed gives 123, well-formed gives the ordinary WinError 53. **The probe hostname must contain no underscore** - an underscore is illegal in a hostname, so Windows returns the very 123 the test reads as failure, and the test fails against *correct* code.
- **Forward slashes**: `\\?\C:/Users/x` does not resolve at all - `exists()` returns **False** and `open` says "No such file or directory", so the file looks *absent* rather than erroring. Tk's `askdirectory` (the fallback folder picker, used whenever the COM shell picker fails) returns forward slashes on Windows.
- `normpath` fixes both and also resolves `.` / `..`, which the prefix would otherwise take literally. The `Path(s).is_absolute()` gate is kept deliberately: it is False for a drive-relative root like `\Users\x`, which cannot be an extended-length path at all - widening it to `ntpath.isabs()` would emit the invalid `\\?\\Users\x`.
- **`core/sync_manager.py` had its OWN COPY of this function**, and all 26 manifest call sites used that copy - so the fix reached none of the sync database until the duplicate was made an alias. Two tests now pin it: one asserts the two agree on every probe, one bans a hand-rolled `'\\?\' + path` anywhere (`converters/archive.py` had one). **A shared path primitive with two implementations is a fix that lands on half the app, silently.**

## Nothing may park the app on a number a server chose, or on a process that stopped talking
- **`Retry-After` is attacker/misconfiguration-controlled** and was obeyed literally: a header of `86400` parked the download on a one-second cancel-polling loop for a **day**. `core.canvas_logic.parse_retry_after` clamps to `MAX_RETRY_AFTER_SECONDS` (120) and is used by BOTH engines (`sync/execution.py` had its own hand-rolled `int()`). It returns an **int** because the value is both shown to the user ("retry in 3s") and counted out a second at a time - and because the producer formats it into `RATE_LIMIT:{wait}` which the consumer parses back, where a float made `int()` raise *inside the handler meant to absorb the error*.
- **ffmpeg gets no timeout flags** (a version that rejects them would break every Panopto download), and the poll loop had no wall-clock bound - so a stream that simply stopped sending hung for ever. Interactively the user can cancel; **the daily auto-sync runs unattended**. `panopto/stream.py` now bounds it with `_STALL_TIMEOUT_SECONDS` measured as **growth of the `.part` file**, not elapsed time, so a genuinely slow download is never killed. `_stop_ffmpeg` terminates *then reaps* - `kill()` without a following `wait()` leaves the child unreaped and may hold the handle that makes the `.part` cleanup a silent no-op.
- **A test for "this terminates" must be able to FAIL rather than hang.** The first version called the download directly, so removing the watchdog made the test hang for the full 900s mutation timeout instead of reporting. It now runs on a thread with a join timeout.

## Never destroy a LIVE session's processes on the strength of `clean_exit` (2026-08-07)
`core/health_log._reap_recorded_orphans` kills the child processes the previous session recorded. Its identity proof (pid + image name + creation time, plus the WebView2 `--user-data-dir`) is sound, but it was answering the wrong question first: **`clean_exit: False` does not mean "that session died"** - it is what the state file says for the whole time a session is RUNNING (`_save_state` writes it on every sample; only `session_end` clears it).
- So a second instance booting beside a live first one reads the first one's CURRENT children and kills them: the running window's **WebView2 process**, or the **ffmpeg / transcription worker of a sync in flight**. Reproduced directly against the real function - a live child recorded, reaped and dead in one call.
- `start.py`'s single-instance guard normally prevents a second instance, but it **fails OPEN by design** in three ways (mutex creation failure, the `CANVAS_DL_ALLOW_MULTI` escape hatch, any exception on the flock path), and its Windows mutex is **session-local** - two Terminal Services sessions for one user share `%APPDATA%` but not the mutex. A reaper that can destroy a live session must not rest on a guard that is allowed to let a second instance through.
- **The guard is LIVENESS, and it is the only thing that changed.** The per-child identity proof was never the weak part - it cannot help here, because for a live session those children genuinely DO match. The cost of skipping a reap is one leaked process the next clean launch collects; the cost of a wrong kill is a user's window vanishing mid-sync.
- **A missing/unreadable pid FALLS THROUGH to the identity proofs - refusing there was tried first and reversed on evidence.** Refusing looks safer and is not, for two reasons found by running the existing suite: `_save_state` has written `pid` beside `children` since this module's first commit, so a record with children and no pid **cannot** have come from a live session (the only thing this guard defends against); and four tests in `tests/test_health_log.py` pass no pid, three of which assert a spare - so refusing would have made them **vacuous**, passing with the identity proofs deleted. A guard that disables the tests protecting the code around it is not a safe guard.
- `tests/test_orphan_reaper_liveness.py` covers both directions (a live session's child is spared, a genuinely dead session's orphan is still reaped) and pins the pre-existing recycled-pid and image-name proofs. 7 of 8 mutations caught across both files; the eighth (`_prev_pid = 0` -> `1` in the unreadable branch) is an **equivalent mutant on Windows**, where pid 1 does not exist, so it falls through exactly as the real code does.

## `open(path, 'w')` TRUNCATES first - the settings file was written five ways
`ui/auth.py` persists `canvas_downloader_settings.json` in FIVE places. Three did tmp + fsync + `os.replace`; the two that did not were the legacy token-migration paths in `restore_saved_session`, which run at **startup**, on the very run that moves a token out of the JSON and into the keyring - i.e. exactly when the file is most worth not corrupting. A crash or a full disk between the truncate and the write leaves the user's settings empty. `write_config_atomically(config)` is now the one helper; it returns False rather than raising, because a settings write must not be able to abort a login. The three inline copies are correct and were deliberately left alone (one carries bespoke amber-notice error handling) - the test asserts the INVARIANT ("no write to CONFIG_FILE truncates in place"), so it covers all five regardless of form.

## `import x` inside a function makes `x` LOCAL for the whole function
A reference above that import raises `UnboundLocalError` - and because an enclosing `except Exception` catches it, the symptom is a wrong log message and a silently skipped branch, not a traceback. This audit *introduced* one in `converters/archive.py` (module used `logging` only inside its `except` handler; a new reference above it activated the trap) and caught it only by running the real function - the observed error was `cannot access local variable 'logging'`, on a path where the outer handler then reported "Failed to extract" for an extraction that had actually succeeded. Same shape as the `isolate` bug in `core/canvas_logic.py`. `tests/test_failure_hardening.py` now scans every function for it; **the scanner must take `min()` over the import lines** (`ast.walk` is breadth-first, so the first import it meets is not the earliest in the source) **and skip annotations** (a `-> Path` return annotation is evaluated at def-time in the ENCLOSING scope, so it is never shadowed). Both flaws produced false positives on the first pass.

## A DIRECTORY fails at 248 characters, not 260 - and the app died there first (2026-08-22)
`CreateDirectory` reserves 12 characters so an 8.3 name can still be created inside, so the limit for a FOLDER is `MAX_PATH - 12`. Measured on a machine with `LongPathsEnabled=0`: mkdir accepts **247** and rejects **248**, while a FILE still goes to 260. A course folder therefore fails **twelve characters earlier** than a MAX_PATH analysis predicts, which is why this was reachable with an ordinary CBS course name (110 chars) under an ordinary destination.
- **The download engine's WRITES had been long-path safe for a long time; its directory CREATION had not.** `core/canvas_logic.py:download_course_async` died at `base_path.mkdir()` - **0 files, 1 app error** - before it could reach any of the `aiofiles.open(make_long_path(part_path))` / `os.replace(make_long_path(...))` work that was already correct. **A fix that lands on the writes and not the mkdir looks complete and ships a total failure.**
- **`scripts/check_longpath_gate.py` is the one probe, and it must be run BEFORE believing any long-path result.** It is empirical, not a registry read: enforcement needs the registry value AND the executable's `longPathAware` manifest, and the value is only read at process start. Exit 1 on a masked machine so nothing can sail past it. Re-check the key after any Python or Git for Windows upgrade - both installers offer to enable long paths, which is how the laptop lost the property in the first place.

### `walk_files_long` walks THROUGH the prefix and yields CLEAN paths
`shared/helpers.py`. `rglob` fails two different silent ways: a root over the limit yields **nothing**, and a reachable root with an over-limit file yields the entry whose `is_file()` then answers **False**. Neither raises.
- **The clean-path half is not tidiness.** The manifest walks feed `_path_key`, which compares against stored rows, so a leaked `\\?\` would mismatch every one of them - a "fix" that looks right and quietly corrupts the manifest. Each hit is mapped back onto the caller's own spelling of `root`; nothing is textually stripped.
- **`Path.mkdir(parents=True)` through the prefix was an untested assumption under all 10 mkdir fixes** - pathlib builds parents by walking `.parent`, and the prefix changes what that yields near the drive root. Verified: full chain at 300 chars from a root with no existing parent, idempotent, and a file writable inside it.

### What must NOT be prefixed, each for a different reason
- **Anything handed to a SUBPROCESS.** A real mp3 at **304 characters decodes fine** unprefixed, because `faster_whisper`'s patched `decode_audio` passes the path to **ffmpeg as an argv element** and ffmpeg is a separate process - Python's enforcement never applies. This disproved a finding before it was patched; measure before "fixing" a subprocess path.
- **Office COM paths.** COM rejects the prefix; `office_safe_path` stages to a short name instead. That asymmetry is the point of it.
- **The config dir (16 mkdir sites), measured rather than assumed.** With a 104-character username - the Windows maximum - the tree tops out at **180 chars**, under both limits. Patching them would be churn.
- **`converters/archive.py` opens through a FILE OBJECT**, because its own comment carried two wrong claims: "the archive file itself won't hit MAX_PATH" (a zip in a deep course folder measured 280 chars and could not be opened at all) and a Python-version caveat about `tarfile`. A file object settles both - `open()` handles the prefix and zipfile/tarfile never see a path.
- **`sqlite`'s URI parser cannot express an extended-length path in ANY spelling** - backslashes, forward slashes and percent-encoding all measured failing ("invalid uri authority: %3F"). Only a plain prefixed filename opens it, and that takes no `mode=ro`. Where read-only matters, COPY the db through the prefix to a short temp path and open the copy.

### The SECOND-ORDER audit: auditing the FIXES, not the code (2026-08-22)
Run immediately after the five-layer pass above, on the standing instruction not to see a crash in a week. It found nothing wrong with the *product* fixes and two live defects in the *class* they belong to - which is the point: the productive question at this stage is not "did I patch the sites" but **"can my guard still say NO, and to what?"**

**THE HALF-FIX SHAPE - `path_exists(x)` prefixed, the next line not.** This is what a long-path fix actually regresses into, and it is worse than a plain miss because the existence check PASSES: the file is reported present and the very next statement raises `FileNotFoundError`, which every handler in this repo reads as *absent*. Two live instances, both created by a fix that prefixed the check and stopped:
- **`shared/components.py` `error_log_dialog`** - `core/canvas_logic.py` WRITES `download_errors.txt` through `make_long_path`, and this read it back without. So at depth the app could write an error log and then not read it, rendering *"Could not read ...: No such file or directory"* about a file it had just created. The error dialog is the one screen a user opens when something has already gone wrong.
- **`ui/sync_dialogs.py`** - sized an ignored Panopto recording; the `except OSError: pass` one line below swallowed it, so the dialog reported **0 bytes** for recordings plainly on disk.
Measured at 275/269 chars: `path_exists` True, unprefixed op `FileNotFoundError`, prefixed op fine. Neither is data loss; both are the app lying about its own files.
- **The durable artifact is the SCANNER, not the two fixes** - `test_no_existence_check_is_prefixed_while_its_follow_up_is_not`. It found two and will find the third.
- **ITS WINDOW COUNTS CODE LINES, NOT PHYSICAL ONES, and that is not a detail.** The first version counted physical lines, so the eight-line comment explaining the `components.py` fix pushed the fixed call out of the window - and the guard then PASSED against deliberately reverted code, reporting a live defect as absent. Same trap this file already records for the transcription sweep. **A guard whose reach shrinks when someone explains the code is worse than none**, because explaining is what a good fix comes with. Found by running the control, not by reading it.

**Two blind spots in the guards written the day before**, both latent rather than live, which is exactly why they had to be closed - a guard that passes gets recorded as protection:
- **The mkdir census could not see `os.makedirs`.** It matched `<expr>.mkdir(...)` only, so a module-level creator was invisible; the first `os.makedirs(course_folder / sub)` anyone added would crash the download at depth with the census still green. Fixing it also removed a FALSE positive: `os.mkdir(...)` does match `attr == "mkdir"` and its receiver is the bare module `os`, which can never contain `make_long_path`, so a correctly prefixed `os.mkdir` was being reported.
- **The prefix-LEAK guard could not see `x = Path(make_long_path(y))`** - only the bare form. Nine wrapper-form bindings exist; eight are ints (`getsize`) or bare names (`listdir`) and cannot carry a prefix, one (`archive.py`'s `extract_dir`) is a real prefixed path the guard had never examined.

**Three claims re-measured rather than re-asserted. Two held, one was wrong in my favour and is corrected:**
- **`Path.resolve()` KEEPS the `\\?\` prefix** (measured; an earlier probe said otherwise and *the probe was broken* - a heredoc-mangled literal). This matters because `converters/archive.py`'s zip-slip guard compares `extract_dir.resolve()` against `(extract_dir / member).resolve()`: both sides carry the prefix, `commonpath` compares like for like, benign member INSIDE, traversal BLOCKED. The security guard is sound at depth.
- **ffmpeg ACCEPTS a prefixed output path** - a real 1412-byte MP3 written at 260 chars with the bundled binary. `panopto/stream.py` prefixes `out_path` at the top of `_run_ffmpeg_download` and derives `part_path` from it, so the stall watchdog and the empty-file check both operate on a prefixed path. **This was flagged as a defect and then disproved by reading the full function** - grep saw `os.path.getsize(part_path)` with no prefix on the line and missed that the variable was already prefixed 90 lines up. Had it been real it would have killed every Panopto download in a deep folder after 180s with a message blaming the network.
- **CORRECTION to "the config dir tops out at 180 chars".** That figure counted only the flat config files. The true worst case with a 104-character username is **224** (`cuda_libs/_tmp12/<nvidia wheel>.whl`), and the deepest DIRECTORY - which is what the 16 unpatched mkdir sites actually create - is ~163. Both are still inside their limits (files 260, directories 248), so **the decision not to patch them stands and is safer than the number I first wrote**. It holds for a reason that was never recorded and should be: **both layouts are FLAT**. Models are streamed to `panopto_models/<id>/<short name>` by hand, NOT via `snapshot_download` - the HuggingFace cache layout would add 125 characters of `models--Org--Name/snapshots/<sha>/` and put the total at 272, over both limits. Anyone switching that fetch to `snapshot_download` re-opens this.

**`compute_local_md5` re-verified end to end at 311 characters**, since edit protection rests on it: EXISTS -> real digest, MISSING -> `""`, LOCKED (exclusive `msvcrt` lock) -> `None`. The three-valued contract survives depth intact, and `_classify_local_modification` reads the difference. Also confirmed there is only ONE file hasher in the app - `secondary_content_sig` hashes Canvas-side STRINGS, not a path - so the divergent-primitive failure this repo has hit three times does not apply here.

**Where the sweep came back CLEAN** (350 unprefixed path calls triaged; do not repeat): `core/sync_manager`'s `history_path` (config dir), its `item.is_dir()` (the item comes from a prefixed `iterdir`, so it is already prefixed), both `shutil.disk_usage` sites (destination ROOT, and `_check_disk_space` fails OPEN), `converters/verify.py`'s two delete gates (both prefixed), `shared/components`'s log-tail readers (config dir), and `shared/shortcuts`'s `tmp_long`.

## Deep crash/leak audit (2026-08-08): every finding was a class this file ALREADY documents
