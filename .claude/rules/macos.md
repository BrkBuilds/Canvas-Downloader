## The macOS Keychain prompt must never be on the SCRIPT THREAD (2026-08-21)
`restore_saved_session()` runs during init, on the Streamlit script thread, before a single element renders - and `keyring`'s macOS backend calls `SecItemCopyMatching` with **no UI-suppression flag**. When the saved item's ACL does not trust the running binary that call **BLOCKS on a system prompt**, so the script never finishes and the frontend has nothing to render. Measured in the PACKAGED app on macOS 26.6.1, frames captured:

| t | what the user saw |
|---|---|
| 0-30 s | boot overlay, "Connecting…" + spinner |
| **30-90 s** | the overlay's absolute cap fires and the window is **COMPLETELY EMPTY** |
| Deny, or the 90 s watchdog | the login page, **with no explanation at all** |

Nothing on screen connected the empty window to the Keychain dialog, and `_load_fallback_token` is a deliberate no-op off Windows - so a denial silently means "go and find a Canvas token again".

- **It fires on every app UPDATE, not once.** The bundle is ad-hoc signed (`TeamIdentifier=not set`), and **both** halves of a keychain item's access control key on the code signature: the trusted-application list *and*, since 10.11, the **partition list**.
- **TWO ESCAPES ARE MEASURED AND CLOSED - do not re-derive them.** `security add-generic-password -A` (trusted-app list `<null>`) **still prompts**: the ACL dump shows `partition_id: apple-tool:`, and the partition list gates access independently. And the app **cannot silently repair its own ACL** afterwards - the delete half of delete+add needs authorisation we do not have and fails **-25244**. That failure is SAFE (the item survives), which is why the attempt is UI-suppressed or not made at all. So while the app is ad-hoc signed the prompt is **unavoidable**; only its cost is fixable.
- **`Allow` and `Always Allow` are not interchangeable, and that is the single most valuable thing the notice says.** Measured by re-reading with UI suppressed after each click: **`Allow` leaves the ACL UNCHANGED**, so the prompt returns on **every launch, for ever**; **`Always Allow` updates it** and the prompt does not come back until the next update. A student who picks the safer-sounding button gets the worse outcome permanently, and nothing else in the product would ever tell them.
- **The fix is a NON-INTERACTIVE probe, and it is a structural guarantee rather than a tuned timeout.** `keyring_get_without_prompting()` flips `SecKeychainSetUserInteractionAllowed(false)` around the read, so "macOS would put a modal in front of the user" stops being an unbounded block and becomes an error we see in milliseconds - **4.3 ms** on success, **9.6 ms** when a prompt would be needed. `needs_prompt` means *exactly* that: a missing item, or any other failure, answers `(None, False)`, because prompting cannot fix those.
  - Suppression is **PROCESS-GLOBAL**, so the window is held under `_keychain_ui_lock` and restored in a `finally`. A probe that finds the lock already taken **returns `(None, True)` rather than waiting** - waiting for the in-flight unlock is the exact blocking this function exists to remove.
  - **The seam is platform-independent on purpose.** `restore_saved_session` calls `keyring_get_without_prompting` on every platform (Windows delegates straight to the old watchdogged read). Had the darwin branch been the only caller, a regression would **pass on Windows and fail only on a Mac** - which is precisely how this class of bug survives in this repo.
- **The prompt is raised as the LAST statement of `render_login_page`, and the position IS the fix.** The script run ends on the next line, so the explanation has already been emitted and the window paints before the system dialog can land on top of it. Starting it any earlier risks the dialog appearing over a window that is still empty - the experience being removed. Same discipline as "invoke a dialog after every event-container write".
- **The notice must never write to the EVENT container.** It polls via `@st.fragment(run_every=1.0)`, and a fragment rerun **rewinds that container's write index** - so a style-only `st.html` or an `st.toast` inside it would land on a neighbouring stylesheet's host and strip a component of its CSS. Its stylesheet therefore lives in the login page's **unconditional** block (a conditional one shifts every later host by one), and the fragment emits exactly ONE element in every state.
- **The resolved token is NOT consumed - found by driving the real app, not by the tests.** The unlock state is process-global (a background thread has no `ScriptRunContext`) while `keychain_unlock_pending` is per SESSION, so a second session - a reload, or a second window - set pending, found the unlock already `ok`, received an **empty** token because session one had taken it, and landed on a bare login page with no notice. Keeping the value costs nothing (it is already in the Keychain and in session one's `api_token`) and `reset_keychain_unlock()` clears it whenever the credential is dropped, at **both** the logout and `force_reauth` sites.
- **`store_token` is deliberately NOT given the same treatment.** Its pre-read exists to *skip a write that cannot change anything*, and that skip is what stops a refused write destroying the credential (`set_password` on macOS is delete-then-add). Making that read non-interactive would trade a safe prompt for a **destructive** write, because the write's own delete prompts anyway. So a user who denies and then pastes a fresh token still meets one prompt at login - contextual, user-initiated, and bounded. Stated rather than fixed.
- Verified end to end in the real app: post-update prompt -> **painted login page + notice in 1.12 s**; the user clicks Always Allow -> the app **signs itself in with no app interaction**; next launch -> **1.15 s, no notice, no dialog**, and the suppressed read confirms the ACL really was updated.
- Covered by `tests/test_keychain_unlock.py` (33) and `scripts/_mutate_keychain_unlock.py` - **23/23 caught**, so re-run the mutation pass rather than just the suite. **Two survivors in the first pass were real gaps in my own tests**, and both are worth remembering: counting keychain READS is not a test of single-flight (the workers serialise on the UI lock, so exactly one read happens either way - count **THREADS**), and nothing checked `app.py`'s call site at all, so deleting the adoption call while leaving `from ui.auth import adopt_pending_keychain_unlock` above it satisfied every test.

### A mutation pass needs a per-mutant TIMEOUT, or a hanging mutant strands itself
This file already warns that a concurrent commit can capture a mutant. The same damage arrives from the pass's own runtime: a mutant that makes the code **block** (here, the probe taking the UI lock blocking, deadlocked against a test that holds it) hangs pytest, the pass is eventually killed from outside, and its `finally` never runs - so the **mutant is left on disk**, indistinguishable from real code. That happened while this set was being written and was caught only by grepping the source for `if False:` afterwards. `subprocess.run(..., timeout=...)` bounds it and a timeout counts as CAUGHT (a mutant that hangs the suite is one the suite noticed); the runner also asserts the restore actually took. The other half is the test's own duty, which this repo already states for the ffmpeg watchdog: **a test for "this does not block" must run the call on a thread with a join timeout, so a regression FAILS instead of hanging.**

## An AppleScript string literal is escaped in ONE place, because the rule had three (2026-08-10)
Found by driving every macOS branch from Windows (`sys.platform`/`platform.system()` answered as darwin, real functions throughout - the same technique that caught the macOS Office delete-gate miss). An AppleScript string literal cannot span lines, so a raw `\n` **or `\r`** inside one is a SYNTAX error that kills the whole script; a bare `"` or `\` is an injection. Three places build such a literal, all three agreed on quotes and backslashes, and exactly one flattened only `\n`:

| builder | `\\` `"` | `\n` | `\r` |
|---|---|---|---|
| `engine/applescript_bridge._as_posix` | ok | ok | ok |
| `shared/helpers.native_folder_picker` | ok | ok | ok |
| `engine/notifications._show_macos_notification` | ok | ok | **missing** |

- **The one that was wrong takes a Canvas COURSE NAME.** `sync_ui.py` builds the daily-sync notification body as `f"{n} new files in {courses[0]['name']}."`, so a lone `\r` anywhere in a course name (or a user's pair label) reached the literal intact. Measured against the real function: the emitted script was `display notification "Body Lec\rture.doc" ...` - unterminated, rejected by osascript.
- **It fails SILENTLY, twice over.** The osascript call sits in a `try/except Exception` that logs at **debug** level, and it is fallback **#4 of 4** (UNUserNotificationCenter → NSUserNotification → pync → osascript), the first three passing the string as an object and so unaffected. So the notification simply never appears and nothing anywhere says why. That bounds the severity - no data loss, and only on a machine where the three PyObjC paths have already failed - but it is the *class* that matters, not this instance.
- **Same divergent-primitive shape as `make_long_path`'s duplicate in `core/sync_manager.py`**, and the same lesson: a rule written more than once is a rule some caller is following an old version of. `engine.applescript_bridge.applescript_string()` is now the single implementation and `_as_posix` is `applescript_string(path.resolve())`.
- **`applescript_bridge` is the right home because it imports nothing from the app at module level.** `shared/helpers.py` and `engine/notifications.py` both reach it, and it reaches `shared.helpers.get_config_dir` back - safe only because every one of those imports is function-scoped. A module-level app import here turns all three into a cycle, so the test checks the **level**, not merely the presence: a blanket ban would flag the existing lazy import and read as a violation where there is none.
- **Order is load-bearing**: backslash before quote. Quote-first produces `a\"b`, and escaping backslashes after that turns the escape itself into `a\\"b`, which closes the literal. A line break becomes a **space**, never `''` - deleting it would silently join two words of a name shown to the user.
- **The copies must be deleted, not merely bypassed.** A dormant `.replace('\\', '\\\\')` chain sitting beside the shared call is exactly how the rule drifts apart again, so a test rejects any `.replace()` of `\`, `"`, `\n` or `\r` inside those two functions.
- `tests/test_applescript_string_escaping.py` (17); all **8** mutations of the real code are caught, including each caller reverting to its own escaper - so re-run the mutation pass rather than just the suite. **Not reproducible from Windows at runtime** (`import subprocess` lives inside notifications.py's `if system == 'Darwin':` block, so off macOS the name is absent and path 4 dies on a `NameError` inside its own handler); the test injects it, and asserts the command was actually captured, because without that the check passes against a script that was never built.

## iCloud "Optimize Mac Storage": SUPPORTED, and now pinned by tests (2026-08-20)
A student on a cheap small-SSD Mac is a core persona, and macOS EVICTS their
course files to free space: the name and size stay, the bytes do not
(`st_blocks == 0`), and **the first process to READ one silently downloads it
again**. So on such a folder hashing a file is not cheap - it is a network fetch
and a disk refill, and it undoes the very setting the student turned on.

**Measured on macOS 26.6.1 against a real iCloud account, driving the REAL
`SyncManager`** (an account was created on the audit box for this; the two
previous runs had none, which is the only reason this stayed open):

    analysis, nothing changed on Canvas    0 of 10 files materialised
    analysis, ONE genuine update           1 of 12   (only the changed one)
    heal_manifest after a RENAME           1 of 12   (only the renamed one)
    os.replace onto a dataless target      works, content correct
    read of a dataless file                correct md5 in ~0.9-1.35 s -> 'clean'

- **macOS 26 uses DATALESS FILES, not `.icloud` placeholder stubs.** The listing
  after eviction shows the real names and nothing else, so an evicted file does
  NOT read as a missing file plus an untracked stub - the failure that would
  have made every sync re-download the course. (Not verified on macOS 13/14.)
- **The engine passes because of three properties nothing was pinning**: the
  folder walks take `stat().st_size` and never open a file; candidate md5s are
  explicitly lazy (`'md5': None  # Lazy compute`); and the update path hashes
  only what `_is_canvas_newer` already selected. A reasonable refactor - *"just
  hash everything up front, it's simpler"* - would silently turn every sync into
  a full re-download for these users, **and no existing test would have failed**.
  `tests/test_icloud_dataless.py` is now that contract, and it is PORTABLE: it
  counts calls to `compute_local_md5` rather than needing iCloud, so it holds
  the line on Windows and in CI, where the failure it prevents is invisible.
- **Hashing the updated file is REQUIRED and must not be "optimised" away.** It
  is how an edited local copy is told from a clean one, which is what
  `_NewVersion` rests on - and a dataless file can absolutely contain the user's
  edits, because edits sync to iCloud and are then evicted. The materialisation
  is the price of the edit-protection guarantee. What must never happen is
  hashing its NEIGHBOURS.
- **A materialisation that FAILS is safe by construction.** `compute_local_md5`
  catches `OSError` broadly - which is what matters, since a failed fetch
  surfaces as `EIO`/`ETIMEDOUT` and not `PermissionError` - returns `None`, and
  `_classify_local_modification` biases to `'modified'`, i.e. `_NewVersion`.
  The local copy is preserved; the cost is a sibling, never an overwrite.
  Narrowing that handler would let the error escape into `analyze_course`, which
  has NO try around the call and would abort the whole course.
- **`_is_canvas_newer` treats same-size-newer-timestamp as a metadata touch**
  and returns False. A probe that "changes" a file by bumping only its timestamp
  therefore measures nothing - the first version of this measurement fooled
  itself exactly that way and nearly recorded "0 materialised on an update" as a
  good result. A test fixture here must change the SIZE.
- **Detect dataless with `st_blocks == 0` at a nonzero `st_size`.** Do NOT use
  `brctl status`: on a freshly-enabled account it returns *"Client zone not
  found"* for a path that is plainly there, which reads like a broken test. That
  is brctl failing to QUERY, not the file being unsynced - proved by evicting a
  file (blocks 248 -> 0) and reading the correct md5 back.
- 5/5 mutations caught (`scripts/_mutate_icloud_dataless.py`), each a plausible
  refactor rather than a strawman. Re-run the pass, not just the suite.

**Still unmeasured**: a real materialisation FAILURE (offline, or an account
over quota). Only its consequence is measured, above. Cutting the network is not
available on a machine reached over remote desktop - it strands the operator and
the agent both.

## Quit only what WE launched - asking the documents cannot answer it (2026-08-12)
Found by driving all three Office apps in the ordinary *"the user is editing while a sync converts"* state. **Word closed the user's document and quit; Excel and PowerPoint did not** - which is exactly why this needed all three to surface.
- **The defaults on a failed property read were the data loss.** `_idle_quit_script` calls a document the user's if it has a path on disk or unsaved changes, each read in its own `try`, defaulting to `hasPath=false` / `isSaved=true` - **which is precisely the definition of PRISTINE**, so an undescribable document did not block and the quit goes out `saving no`. The docstring claimed the opposite ("defaults to blocker … never to a wrong quit").
- **And the documents ARE undescribable.** Measured: before a conversion phase `path=[Macintosh HD:…:MY WORD WORK.doc] saved=false`; after one, **name / path / full name / saved ALL FAIL**. Not stale references - the reads fail inside a single `tell` block. Every app is left holding one such document, and `_force_close_canvas_docs_sync` cannot close it either, because it identifies documents by those same properties.
- **NEITHER default works, and that is the point.** Undescribable-as-pristine destroys a student's unsaved essay; undescribable-as-blocker left all three apps in the dock after every run (measured: exactly that, plus no Recents purge, since the purge declines while an app runs).
- **So stop asking the documents and ask who launched the app** - the rule the product owner chose. An app the user already had open is never even asked to quit; an app WE launched holds only our documents, so an undescribable one there is ours. Stated explicitly as `undescribable_is_ours` rather than left as an accident of the defaults.
- **THE OBSERVATION MUST BE TAKEN AT THE TOP OF `prime_office_automation`, AND THIS IS THE PART A HARNESS CANNOT CATCH.** Priming launches every enabled app with `open -g -j` at run start, so by the time the first conversion asks "was it already running?", **all three are running by our own hand** - the gate then calls them all the user's and quits nothing, which is the exact opposite failure to the one it was added for. Measured in the real app with all three killed beforehand: *"PowerPoint was already running before this run"*, all three left in the dock, 70 of our entries stranded in Recents. Every harness in this repo passed, because they drive the converters directly and never prime. The call in `run_applescript` stays as an idempotent fallback for those flows. `_APP_TRIPLES` (priming) and `_APP_DOC_MAP` (the gate) must keep naming the apps identically or the gate silently stops protecting one; a test pins that.
- **Verified in the REAL APP, both states, course 43660, with converted PDFs deleted first so genuine conversions had to run**: *cold* - `quit sent (1 open doc(s), none user-owned)` for all three, 8/8 re-converted, all quit, Recents 0; *busy* - `left alone (the user already had it open)` for all three, 6/6 re-converted, **all three user documents intact**, 0 failures.
- Second defect, same lean: the `full name` fallback tested `contains "/"`, but Word reports an **HFS colon path**, so it could never fire for Word.
- Verified end to end on all three apps (`scripts/verify_office_end_to_end.py`): **cold** 12/12 converted, all three quit, Recents 37 -> 0; **busy** 12/12 converted, **3/3 user documents survived**, all three left running. `tests/test_office_quit_scoping.py`; all 6 mutations caught.

## …and the observation is PER RUN, taken at EVERY launcher (2026-08-13)
The fix above is only as good as the moment its observation is taken, and that moment was recorded in **one of the three places that can launch an Office app, once per PROCESS**. Three holes, each reproduced against the real functions from Windows with `sys.platform` reporting darwin. This is the same class the section above closed, one level up - which is the playbook's thesis for the fifth pass running: *the productive question is never "what could be wrong" but "which module did the last fix for this class NOT reach?"*
- **`first_run_permission_setup` is a launcher too, and it is the EARLIER one.** It spawns the same `_warmup_apps` (`open -g -j`) and never observed. Both `app.py` and `sync/execution.py` call it at **run start**, reaching `prime_office_automation` only per course, later - so on a machine whose Automation grants are not yet recorded, i.e. **a new user's FIRST run**, the batch launched all three, the later observation saw our own launch, every app read as the user's, **nothing was quit, and the Recents purge declined as well** (it refuses while every app is running). Measured: `alive after the batch: [Excel, PowerPoint, Word]` -> `apps this run will QUIT: NONE`. The D11 symptom, on the run that forms a first impression.
- **`reset_office_priming` cleared every other piece of per-run Office state and not this one**, so run 2 of a session answered with run 1's facts. The dangerous direction is the reachable one: run 1 launches Word and records "ours"; the user then opens Word and starts an unsaved essay; run 2 still reads "ours" and the teardown quits it `saving no`. Run 2 has just had a conversion phase - **the exact state this file records Word's documents as undescribable in** - so the document check, the only remaining defence, cannot see it either. `_office_quit_fired` *is* reset per run by both callers, so the teardown really does fire again. The opposite direction (a stale "theirs") only ever costs an app left in the dock, which is why the fix is to **re-observe** rather than to age or reconcile the value.
- **"Never observed" is a THIRD answer, not a False.** `office_was_preexisting` was `dict.get(app, False)`, so an app we never drove counted as ours - reachable by cancelling before priming ran, and **the teardown fires on the cancelled screens too**. `office_is_ours_to_quit` is now `_office_preexisting.get(app) is False`: observed-and-not-running → quit, observed-and-running → leave, **absent → leave**. That is the correct reading and not merely the safe one; `test_an_unobserved_app_is_not_treated_as_the_users` said so in its own docstring while asserting the opposite, and the behaviour won.
- **The duty sits on `_warmup_apps`, the ONE function that actually launches**, so a future fourth caller is safe by construction rather than by remembering - the same move as `run_applescript` wrapping `_run_applescript_locked` so the lock cannot be forgotten. Both callers *also* observe on their own (calling) thread, because `_warmup_apps` runs on a worker and thread scheduling must not decide correctness. `observe_office_before_launch()` covers **all three apps, not just the ones being launched**: a run's contract widens between courses (`office_contract_from_folder` is per folder), so the app nobody was going to open is exactly the one launched later.
- **`_note_office_preexisting` is double-checked under a lock, first writer wins.** Two callers straddling a launch could both pass an unlocked "not recorded yet" check and let the LATER, post-launch answer win - the one direction that costs a document. The lock is contended at most once per app per run; the fast path never takes it.
- **The teardown STATES the undescribable policy instead of inheriting it.** `_idle_quit_script`'s `undescribable_is_ours` defaulted to **True** while its single call site passed nothing, so the docstring's "the caller passes True only for an app IT LAUNCHED" described a contract nothing enforced. It now defaults to **False** and the teardown passes `True` explicitly, one line under the gate that earns it.
- **A test counts the SITES, not the fix**: `test_EVERY_function_that_launches_an_office_app_observes_first` walks the module for everything that reaches `_warmup_apps` and asserts each observes first. The 2026-08-12 test checked `prime_office_automation` because that is where the fix landed - the same shape as `pdf_looks_real`, written for two delete sites and landing on one for eight months.
- **A harness cannot catch this and did not**: every scenario here drives the converters directly, so the launchers never run. The reproduction was `sys.platform` patched to darwin with `pgrep` and the launcher modelled - which proves the DECISION path only; the "documents become undescribable" half is the 2026-08-12 macOS measurement, not re-measured. **STILL UNVERIFIED ON A MAC**, and filed as such: `MAC_RUNBOOK.md` Phase M1 **step 8** is the procedure, `AUDIT_FINDINGS.md` fp `989c128a238d` is the open work item, and `MAC_OFFICE_FIXES.md` known gap 5 is the honest list. The check that matters is **two runs in ONE session with a dirty document opened in between** - `pkill`ing between them is not a substitute, because the bug is about state inside one process, which is exactly why `scripts/verify_office_end_to_end.py` (cold/busy, one run each) cannot see it as written.
- **The residual case, considered and DECLINED**: the predicate asks "was it running when we looked?", not "did we drive it?", and `_QUIT_TARGETS` is all three apps every run - so an app observed as idle and never touched still counts as ours, and a user opening it MID-RUN is asked to quit. The document check protects them there, soundly: no conversion phase ran for that app, so its documents are still describable and only a pristine blank is quit. A separate "we actually drove it" set would close it exactly, and is a SECOND fact about the same question kept in a second place - which is the bug this file has now fixed twice.

## The Recents purge deleted VALUES and left every entry on screen (2026-08-12)
The function the app relies on to clean up after itself had never removed a single Recents entry.
- Office's start-screen Recent list is driven by rows in `HKEY_CURRENT_USER`, each a node whose **`name` IS the full `file://` URL**. The old code selected `HKEY_CURRENT_USER_values WHERE name='path'` and deleted only value rows: measured on the real registry, **495 value rows removed, 0 nodes** - every entry still listed, now stripped of its values. The whole database held **36** rows named `path`. A half-mutation of Office's SHARED registry is worse than not running.
- Now matched on the node NAME, deleting node + values, behind **three gates**: the marker (a directory name we own), **leaf-only** (so it can never amputate a subtree), and an **`MruUserData` ancestor**. Verified on the real database: **636 removed, 0 of the user's 1041 nodes touched, 0.04 s**.
- **Per APP, not all-or-nothing.** Our entries split PowerPoint 487 / Excel 135 / Word 14, each under `MruUserData/UnsignedUser/<App>/Local/Documents`, so a run cleans the apps that are closed while the user keeps editing in the third. An entry belonging to a RUNNING app is left alone - it would be resurrected from that app's in-memory list on exit - and an entry that cannot be attributed to an app is only taken when nothing is running.
- **The purge lands ~15 s AFTER the last process dies** (wait-for-exit plus the retry pass), and it runs on a daemon thread. Anything measuring the Recents list before that reports a working purge as broken - which cost one debugging cycle here.
- `tests/test_office_recents_purge.py`; 9/10 mutations caught, the survivor documented as equivalent (with every app running the per-app gates already refuse everything, so the early return is only an optimisation).

## macOS gives a user session ONE PowerPoint - two app instances crash it (2026-08-11)

### The marker force-close destroyed documents SILENTLY, and the silence cost an hour (2026-08-21)
`_force_close_canvas_docs_sync` closed Office documents and logged **nothing** - and the AppleScript it runs returned nothing either, so there was no result to log even had the caller wanted one. It is the one teardown step that can end another instance's in-flight conversion.

- **THE GENERAL RULE, and it outlives this fix: absence of a log line is not evidence of absence.** Any argument of the form *"there is no correlate, therefore it was not X"* is only as strong as X's instrumentation, and you usually do not learn how weak that is until it has already misled you. This file's existing rule - *"a bare `except Exception: pass` around UI code is a bug waiting to be invisible"* - has a second half: **a destructive action that reports nothing is a bug waiting to be un-diagnosable.**

An unrecognised answer -> **WARNING**, and the handler (previously `except Exception: pass`) warns with a traceback. ### A correlation can CONFIRM a contaminating cause but can never establish that something is GENUINE (2026-08-21)
Learned adjudicating a live matrix, and it generalises past auditing to any "was this our bug or the environment?" question.
- Correlating failures against a suspected cause's timestamps worked beautifully **where it matched** - 0.77s between one process's `force-terminated` and another's `-609` - which is exactly what made the table feel authoritative. It then produced one entry with no correlate, and the natural reading of "no correlate" was "not caused by that, therefore real".
- **That reading was wrong**, because the most destructive mechanism in the system logged nothing. The correct move was the expensive one: **re-run the case in isolation.** Only isolation can promote something to genuine; correlation can only ever demote it to contamination.
- **A negative control is what makes the comparison mean anything.** When five rows were re-run alone, two of them (never contaminated) reproduced their finding counts EXACTLY - 3 -> 3 and 5 -> 5 - while the two contaminated ones dropped 7 -> 3 and 22 -> 7. Without the unchanged pair, "fewer findings on the re-run" is equally explained by the re-run just reporting less, and the whole exercise proves nothing.
- **Corollary for anything that produces a findings register**: false findings must be marked invalid WITH the disproving evidence named, not quietly dropped. This file already records what a blind oracle does - it does not under-report, it INVENTS - and a register carrying inventions makes every genuine finding in that category unfalsifiable.

## An EMPTY case-sensitive volume answered "case-insensitive" (2026-08-12)
`_probe_case_insensitive` flips the case of a CHILD entry, because a directory's own name lives on its PARENT volume and at a mount point those are two different filesystems. That has one blind spot it cannot cover: **a directory with no child to flip**, where the code fell back to flipping the directory's own name.
- Measured against a real case-sensitive APFS image (`hdiutil create -fs "Case-sensitive APFS"`), probed while still EMPTY: the fallback flipped `/Volumes/CDCaseSens`, resolved it against `/Volumes` on the case-INSENSITIVE root volume, and **returned True for a case-SENSITIVE drive**. - **Reachable**: `_case_insensitive_volume` climbs to the nearest EXISTING ancestor, so a course folder that does not exist yet on a freshly-formatted external drive resolves to the drive's empty root. `_probe_case_insensitive` is `lru_cache`d, so the wrong answer is then frozen for the session even after the first files land.

## `-600` means the app CRASHED, not that it is missing (2026-08-11)

Measured: a stored value, one `set_password` raising `PasswordSetError (-25308)`, and the item reads back `None`. Three things then hid it - `_safe_keyring_set` **returns False rather than raising**, so the login flow's `except Exception` amber notice was unreachable; `_save_fallback_token` is a deliberate no-op off Windows; and the only trace was a `logger.warning` claiming it had been *"Saved to DPAPI-encrypted fallback storage"*, which on macOS is nothing at all. The user's saved login vanished, the next launch showed the login page, and nothing on screen ever said why. **`ui.auth.store_token` is now the ONE writer**: skip a write that cannot change anything (the common path, and the one that turns a refused write into data loss), write, fall back, then **VERIFY by reading back** - so its return value describes the STORED STATE, not one call's return code, which is what makes it safe for a caller to delete its own copy. Both legacy-migration sites now pop the JSON token **only on True**; that is the one run where the JSON copy is the only copy.
  - **The reads use a SHORT watchdog (`_KEYRING_PROBE_TIMEOUT`), the write keeps the full 90s.** macOS can PROMPT on a keychain access - a rebuilt app with a new ad-hoc signature reading the previous build's item, hit on the audit machine - and the prompt blocks. Two full-budget calls would have turned one 90-second login stall into two. Verified in the packaged app's own log: `set_password timed out (90s)` followed by `get_password timed out (5s)`.
- **Office container staging must use a SHORT basename.** `office_container_stage` staged as `work / src.name`, i.e. it shortened the DIRECTORY - which was never the problem, since it discards the user's directory anyway - and preserved the NAME, which was. Word's limit is the **~255-character TOTAL path** and the container prefix costs a measured **91**, so the effective filename budget was ~164 bytes: **any Canvas file named past that could not be converted at all**, silently, per file. Canvas reaches it easily - a lecture title with the course code and week runs well past 100 characters. Now `src.<ext>` / `out.<ext>`; the real name is only needed at the final destination, which the function already moves the product to. A 240-byte name converts.
  - The discriminating measurement, because every other one fits both hypotheses: hold the name at 9 bytes and deepen the staged directory - staged ~220 **converts**, staged ~281 **fails**. And **the unstaged path is NOT a usable control**: with no container macOS demands the per-folder App Data grant staging exists to avoid, so even a short-named control fails there. An intermediate draft of this analysis concluded "component, not total path" from exactly that unsound comparison.
  - `active document doesn't understand the "save as" message` (Word opened it) and `missing value doesn't understand …` (Word did not) are **different** signals; the second is the wedge. Any Office test needs a **fresh Word and its own positive control per case**, or it measures the previous case's wedge.
- **`os.path.normcase` is the IDENTITY off Windows, and the macOS default volume is case-INSENSITIVE** (probed: home APFS and `/tmp`). So `_path_key`'s documented case half did nothing on the platform where `Notes.pdf` and `notes.pdf` really are one file - and one physical file then counted as an untracked orphan AND a missing row, inflating the number the review screen exists to reconcile. Folding unconditionally is the trap: a case-SENSITIVE volume (an ordinary external drive) holds both as two files, and folding there mis-binds a heal. Gated on `_case_insensitive_volume()` - read-only (`samefile` against the case-flipped path, no probe file), `lru_cache`d, climbing to the nearest existing ancestor, **False on any doubt**, which is the previous behaviour exactly. Verified in both directions on REAL volumes, including a case-sensitive APFS image made with `hdiutil`.
- **`version.py` not being bumped is a user-visible defect, not bookkeeping.** `ui/update_banner.py` computes `_is_newer(github_tag, __version__)`, so tagging a release while the bundle says the previous version tells **every user, on every launch, for ever** that an update is available - pointing at the build they are running. `tests/test_version_leads_tags.py` now fails when `version.py` does not lead every shipped tag (skips when no tags are visible, since a shallow clone is not evidence).
- **An idempotence guard only holds if EVERY path goes through it.** `start.py`'s shutdown was a `_shutdown()` behind a `threading.Event`, and the comment said the window-close route therefore closes the health record once - but the `finally` called `session_end()` and `_terminate_child_processes()` directly, bypassing it. Measured in the packaged app: **two identical `SESSION END (clean)` lines** for one START. The `finally` routes through `_shutdown` now.

### The pair being EDITED was identified by its position in the list (2026-08-11)
Investigated on a hunch that `pending_sync_folder` "smelled like" the other identity bugs, and it **proved out**: `editing_pair_idx` is an index into `st.session_state['sync_pairs']`, and the list moves under an open edit form, because the form replaces only its OWN row while every other row keeps a live **Remove** button (and a remove-all path exists). Four positional uses, three of them wrong in a way the user cannot see:
- **The save.** `old_pair = sync_pairs[edit_idx]` decided which pair to repoint, and then `_retarget_saved_pair_lazy` moved that pair's user-given NAME to the new link. `[A,B,C]` edit C, remove A -> `0 <= 2 < 2` is false, so Save Changes fell into the append branch and **created a duplicate pair out of an edit**. `[A,B,C,D]` edit C, remove A -> index 2 is now **D**, so Save Changes **repointed D at C's chosen folder/course and moved D's name**, leaving C untouched.
- **The duplicate check** excluded "self" with `if i != editing_idx`, so after a shift it excluded the wrong pair - which both hides a real duplicate and can block a legitimate save with *"this pair is already on your sync list"*.
- **The mismatch warning** compared against `sync_pairs[editing_idx]`, so it suppressed or invented the course/folder warning for the wrong pair.
- All four now resolve through **`core.pair_labels.pair_key`** / object identity. A NEW session key `editing_pair_sig` carries the link; `editing_pair_idx` survives only as the "a form is open" flag that a dozen `editing_idx is None` checks already read.
- **A vanished pair must CLOSE the form, not fall through.** The old append branch turned a lost edit into a silent duplicate; the form now refuses with a sentence naming what happened. And the render gate matches on the LINK, so an open form **follows its pair** when the list shifts instead of binding to a stranger.
- **THE TRAP MY OWN FIX INTRODUCED, caught by a test rather than by reading**: two "Add Course" buttons popped `editing_pair_idx` and not the new sig. Once the form is matched on the link, a surviving sig makes *Add Course* open the **edit** form on the previously-edited row. `editing_pair_sig` must be cleared wherever `editing_pair_idx` is - `tests/test_ui_leak_and_pair_scoping.py` counts the clear sites in each file and fails when the two disagree, which is the only reason this was found.
- Covered by that file (39 tests); all **7** mutations caught, so re-run the mutation pass rather than just the suite.

### A folder's FILE FILTER decides what the analyzer may even consider (2026-08-11)
Reported as *"seventy six new files, and they have not been added to the course since I downloaded it right before"*. Reproduced from the folder's own manifest and debug log, and it was permanent rather than cosmetic - the same 76 on every sync, for ever.
- **The mismatch**: the download engine skips Canvas **Pages** and module **links** outright under the "Slides & PDFs" filter (`file_filter == 'study'`), while `_get_files_from_modules` - the scan that feeds the sync ANALYZER - enumerated them unconditionally. So the diff compared Canvas against a manifest that could never contain them. Evidence from course 43660: `sync_contract file_filter: "study"`, `secondary_content_contract` all false **and correctly honoured** (`enabled=[none]` in the log), `download_mode flat`, **0** manifest rows for `.html`/`.webloc`, on disk 56 pdf + 51 pptx + 11 pptm and no html/webloc at all, log `Analysis complete: 76 new | 0 clean updates`. Accepting them would have turned the folder into a shape the user never configured.
- **THE RULE WAS WRITTEN IN SIX PLACES AND THE SIXTH DISAGREED** - three branches in `download_course_async`'s module walk, two in the folder-structure walk, one in the metadata scan. `core.canvas_logic.module_item_in_scope(item_type, file_filter)` is now the only definition and all six ask it; a test COUNTS the call sites, because a fix that lands on five of six is invisible in review. The first pass here found only three of them.
- **OUT OF SCOPE IS NOT IGNORED, and that distinction is the design.** `is_ignored` records a decision the USER made; these were never offered to them. Out-of-scope items are dropped before the diff and appear nowhere - not as new, not as ignored. The alternative (mark them ignored) floods the count with 30-70 entries the user never chose against and destroys the meaning of the one number they rely on.
- **The scan's `file_filter` defaults to `'all'`, deliberately permissive**: a folder with no stored contract may show MORE than it should, never silently hide a file. A corrupt contract falls back the same way rather than raising mid-analysis.
- **DECIDED (product owner, 2026-08-11): one folder, one configuration, no widening.** There is no UI to change a folder's scope after the fact - the two filtered modes are deliberate, uncommon choices, and a re-configuration flow is complexity for a fraction of users. Re-download if you want a different shape.
- **RESOLVED the same day by the section below** - which also found that the missing files half was not merely untidy but was actively widening filtered folders. Read that section, not this line.

### The FILES half of the same rule, and it was widening folders one file at a time (2026-08-11)
The paragraph above closed with "`analyze_course` never applies `file_filter` to Files-tab files at all", filed as a tidiness debt whose only cost was 23 mislabelled rows. It was not. Driving the real analyzer showed the same defect as the Pages/links half, live and permanent:
- **A file uploaded to Canvas AFTER the initial download has no `is_ignored` stub, so it was offered as NEW** - and **`sync/execution.py` contains no file filter at all**, so selecting it downloaded it. Measured: a new `Groupwork.xlsx` in a `study` folder came back in `new_files`. A "Slides & PDFs" folder therefore drifted toward All-Files one lecturer upload at a time, silently, which is precisely the shape the product owner ruled against ("one folder, one configuration").
- **The stubs themselves were reported as IGNORED and the dialog offered to RESTORE them** - 23 in a real folder - a decision the user was never asked to make, behind a button that could not do what it said (the analyzer would decline to produce the file).
- **`file_in_scope(disk_name, file_filter)` is the FILES counterpart of `module_item_in_scope`**, and the allowlist existed by hand in **five** places: the download gate, `count_course_items`, `get_course_total_size_mb`, Quick Sync's own re-filter, and `app.py`'s scan. Two of them read the raw `filename` where the engine writes **`preferred_disk_name`**, which APPENDS the real extension when the curated display name lacks it - so a file shown as "Lecture 1" and stored as "Lecture 1.pdf" was counted one way and downloaded another. Same divergent-primitive shape as `make_long_path`'s duplicate and the three AppleScript escapers.
- **Scope is enforced ONCE, in `analyze_course`** - the only place both the Review and Quick Sync flows pass through, so they cannot disagree and one contract read decides. Quick Sync's `apply_file_filter` is **deleted**, not kept as a backstop: two enforcement points each reading the contract independently is exactly how the six-site version got one site wrong.
- **The gate is `real_canvas_file_id`, NOT `id > 0`.** It is already this app's answer to "is this a real Canvas FILE?", and it says yes for the `attachment` band - which an isolate-mode attachment arrives under in the ANALYZER while the engine downloads it under its real positive id and filters it there. Gating on the sign leaves every out-of-scope attachment permanently new. Every other synthetic band is an ENTITY (assignment, quiz, announcement, …) governed by the **secondary-content contract, which `_canvas_content_phase` does NOT gate on `file_filter`** - so scoping those by extension recreates the identical bug in mirror image, for `.html` exports. `sync/execution.py`'s size gate independently hand-rolls the same predicate (`_gate_id > 0 or secondary_id_type(...) == 'attachment'`), which is corroboration that this is the engine's own notion of a real file.
- **CUSTODY OUTRANKS SCOPE.** The rule answers *"may this folder GAIN this file?"*, so a row with a `downloaded_at` keeps its tracking whatever its extension - reachable by a Canvas-side rename, which keeps the id and can change the suffix. Dropping it would silently stop reporting updates for a file the user holds.
- **The reclassification is a QUERY, not a migration.** `get_ignored_files` asks the folder's own contract, so rows written before this version are covered for free, the answer follows the folder instead of being frozen at whatever moment a migration ran, and there is no irreversible write to get wrong. Nothing is rewritten - a test asserts the row survives untouched and only its REPORTING changed. A damaged contract falls back to `'all'`, i.e. lists everything: hiding a decision the user really made is the unrecoverable direction.
- **`file_in_scope` must URL-unquote, because `_sanitize_filename` does.** The engine asks about the SANITIZED name and the analyzer plus both estimators ask about the raw one. Measured: `Lecture%2Epdf` sanitizes to `Lecture.pdf`, so the engine downloads it while an un-unquoted check saw no extension and dropped it - **the silent-missing-file direction, worse than the bug the predicate exists to fix**. Canvas serves URL-encoded filenames routinely (this file already records `'Klyngevejledning+-+Upload.pptx'`). Unquoting inside the predicate rather than at the six call sites is what makes them agree by construction; none of the sanitizer's other steps can change a short extension.
- **`.pdf` is the discriminator that separates this allowlist from the PowerPoint CONVERTER's input set.** Five other sites list `.ppt/.pptx/.pptm/.pot/.potx` WITHOUT `.pdf` (`converters/post_processing.py`, `engine/applescript_bridge.py`, `shared/helpers.py`, `sync/execution.py` x2) - a different concept that must never be merged, because a PDF is not converted to PDF. The single-definition test requires all three of `.pptm`, `.potx` and `.pdf`, and still caught the genuine fifth copy in `app.py`.
- Covered by `tests/test_folder_scope.py` (70); all **22** mutations caught.

### A name a function READS that nothing BINDS is a guaranteed crash - and the Pages fix shipped one
The 76-file fix added `module_item_in_scope(item.type, file_filter)` to `_get_files_from_modules` - where **`file_filter` is not a parameter of that method, is never assigned in it, and is not a module global**. A `NameError` on every module Page or link, in the metadata scan that feeds the sync analyzer, i.e. on most real courses. **The whole suite passed**, because every test of that fix asserted source SHAPE and the shape was right; the browser harness passed a file list straight to `analyze_course` and never called the scan.
- Same class as the `isolate` bug this file already documents, and the second time it has cost a release gate. `tests/test_unbound_names.py` now asserts the property across the whole tree: for every function, every name it loads is bound by that function, an enclosing function, the module, or builtins. **The defect itself is its positive control** - a scanner that reports 0 on a fixed tree proves nothing.
- Deliberately narrow: it catches "bound NOWHERE reachable" (`NameError`), not "bound only on some paths" (`UnboundLocalError` - the `isolate` bug's other half), because deciding reachability in general needs flow analysis and would misfire on ordinary early-return code. A module with a star import is skipped rather than guessed at.
- The false-positive set is the interesting part and is all parametrised: closures, a global defined AFTER its reader, `global`/`nonlocal`, comprehension and lambda targets, walrus, `with as`, `except as`, `*args/**kwargs`, function-scoped imports (this repo's cycle-breaker), match captures, and a method reaching a class attribute through `self`. A class body's names are NOT visible to its methods, so methods are visited with the ENCLOSING scope, not the class's.
