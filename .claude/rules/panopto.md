# Panopto discovery, download and transcription

> Extracted from CLAUDE.md. Loads only when Claude opens a matching file.
> Each entry states the mechanism, the measurement, and why the obvious fix is wrong.

## Do NOT put a stall watchdog on transcription - decided 2026-08-07
`panopto/stream.py`'s ffmpeg download gets one (see above) because the `.part` file grows continuously, so "no new bytes for 180s" is a reliable wedge signal. **Transcription is the opposite and must be left alone.** `transcribe()` emits a progress event per WHISPER SEGMENT, and before the first one there is a long silent stretch while faster-whisper loads (or downloads) a model that can be hundreds of MB. On a weak CPU with no GPU - the machine this was audited on - a watchdog generous enough not to kill a legitimately slow transcription is too generous to catch anything, and a tight one kills real work. The loop already polls `is_cancelled` every 0.3 s, so a user can always stop it; the residual risk is an unattended daily sync wedging, and that is the better trade. The worker's other failure modes ARE bounded: stderr goes to a temp FILE (a full pipe can never block the child), stdout is drained on a thread, a cancel does `kill()` + `wait(timeout=10)` before cleanup so the `.part` sidecars are not locked, and an exited-but-pipe-inherited worker is abandoned after a 3 s grace.

## A UI cancel is a `BaseException`, so cleanup after the loop is not cleanup (2026-08-09)
Found by the LIVE audit cancelling a real transcription, and it is the second round on this same `.part` sweep - the first round fixed the two exits it could see and left the one users actually take.
- **Clicking Cancel does not merely set a flag; it STOPS the script run.** Streamlit does that by raising `RerunException` / `StopException` from the next `st.*` call, which happens inside the `progress()` callback - i.e. *inside* the transcription loop. Both derive from `BaseException`, so nothing in `panopto/runner.py` caught them and they propagated **straight past the sweep**, which was ordinary statements after the loop carrying a comment claiming it covered "every route out of the phase". It covered every `break`; it covered no exception. The sweep is now in a **`finally`**, which is what that comment always meant.
- **The log is the tell, and its ABSENCE is the evidence.** On a normal cancel the phase writes "Transcription cancelled by user" or at least `transcribe_done`; on this one the debug log simply **ENDS** at `Download cancel event cleared`, mid-recording `[3/30]`. Nothing ran after the exception. Measured on course 43660: `<name>.txt.part` (8416 B) and `<name>.srt.part` (16536 B) left in the student's folder, **unlocked** - calling `_clean_part_files` by hand removed both instantly, which is what proves the sweep was never reached rather than having failed.
- **Why a leftover is worse than untidy**: `panopto/runner.py`'s own comment states the engine deliberately ignores `.part` artifacts everywhere - never healed onto a manifest row, never auto-discovered, never counted as study material - so *"nothing would ever remove or even mention them again"*.
- **The same cancel exposed a LATENT long-path bug, and it is the classic asymmetry**: every WRITE in `panopto/transcribe.py` goes through `make_long_path` (the sidecars are opened with it and committed with it) and the DELETE did not. That fails in the most misleading way available - on a default Windows install (`LongPathsEnabled = 0`, i.e. most users) a path over 260 chars raises ERROR_PATH_NOT_FOUND, Python surfaces it as **`FileNotFoundError`**, and the retry loop reads that as *"already gone"*: no removal, no retry, **no log**. The audit measured **259 paths over 255 characters** in that one course and the two abandoned sidecars were **341**. It did not bite on the dev box only because it has `LongPathsEnabled = 1` - the identical reason `office_safe_path`'s long-path bug survived. When a path-length fix "cannot be reproduced", check that registry key first.
- **The tests that were already there passed against BOTH defects**, because they anchored on `_clean_part_files(` appearing within **1800 characters** of `progress("transcribe_done")`. That is true of a sweep in a `finally`, of a sweep after the loop, and of a sweep that never runs - and documenting the fix pushed the call out of the window, so three of them then reported the sweep as *missing* when it was right there ("a brittle test anchor reads like a missing guard", again). They now resolve the sweep through the **AST** and assert the property that matters: that the call sits inside a `Try.finalbody`.
- `tests/test_transcribe_partial_cleanup.py`; 5 of 6 mutations caught, including one for each original defect. The survivor - `break` -> `continue` on the `FileNotFoundError` branch - is an **equivalent mutant**: on a genuinely absent file it spins six cheap iterations with `last_err` still `None`, so the outcome and the logging are unchanged.
- **The CRASH path does not sweep - only CANCEL does - and what contains that is a COUNT of one (measured on macOS 26.6.1, 2026-08-20).** Driving a real SIGSEGV into a live worker - which is exactly what an uncatchable native crash looks like, and the whole reason this runs out of process - confirmed containment works: the parent survived, raised `TranscriptionEngineCrash(exit_code=-11)`, faulthandler dumped the C-level traceback into the debug log, and the child was reaped. But `transcribe_in_subprocess` returned with **both `<name>.txt.part` and `<name>.srt.part` still on disk**; its sweep lives on the cancel branch, not in its own `finally`.
  - It is not user-visible today because there is **exactly ONE production caller** (`panopto/runner.py:_run_panopto_batch`) and its phase-level `finally` sweeps every task on the way out. So the guarantee rests entirely on the caller, and a second caller added anywhere would leak on the crash path with nothing failing - the same shape as `pdf_looks_real` landing on two of three delete sites and surviving eight months.
  - **Do NOT "fix" this by adding a sweep inside `transcribe_in_subprocess`'s own `finally`.** The runner retries a GPU crash on CPU by `continue`-ing to the SAME recording, and the engine-level function cannot tell a retry from an abandonment - sweeping there would delete work the retry is about to reuse the paths for. The phase is the boundary the tasks are already independent across, which is the same reasoning as `_run_phase` in post-processing and `_sec_category` in the secondary-content loop.
  - `test_every_caller_of_the_subprocess_runner_sweeps_in_a_finally` encodes the RULE rather than the count, so a legitimate new caller is fine provided it sweeps; `test_the_subprocess_runner_has_at_least_one_production_caller` stops it going vacuous at zero sites. `scripts/_mutate_transcribe_caller_sweep.py`, **4/4 caught** - and the mutant that justifies the test is the one older tests miss: a plausible `_retranscribe_one()` helper added outside the phase.

## The Panopto **Shortcut** output: a link file is a first-class kind (2026-08-07)
`output_url` sits beside mp4/mp3/txt/srt as the FIRST toggle on the Section 4 card. It costs no bandwidth, no disk and no time, and it answers what a transcript cannot: take me back to the lecture, with the slides, the screen capture and Panopto's own search still attached. Framed as a companion, never a substitute - it is a pointer, so it dies with your Canvas/Panopto access, which is precisely when people want the offline copy.
- **The destination is frequently NOT free, and missing that shipped the feature as a silent no-op.** `core/canvas_logic.py:_create_link` already writes a `.url` for every Canvas **ExternalTool** module item - and a Panopto lecture IS an ExternalTool item named after the lecture. In the *match* layout the Panopto pass therefore computes a path Canvas has already filled. Measured on course 43660 in the real app: **36 recordings discovered, 34 identically-named `.url` files on disk, 0 shortcuts written, 0 manifest rows**, and a completion screen that mentioned Panopto not at all. Every unit test passed. **Overwriting is not the fix** - that file belongs to the Canvas file sync, which tracks its `content_sig` and would rewrite it next run, two subsystems clobbering one path for ever. `panopto/shortcut.py:resolve_shortcut_path` adopts a link WE produced wherever it sits, else takes the first free name, stepping over anything foreign - so the collision case lands at `<title> (Panopto).url` beside the Canvas one. The runner and `sync_plan._find` both ask that one function; computing it twice is how the writer and the analyzer stop agreeing, and the symptom is a link rewritten on every sync for ever.
- **`kind` is the extension for every other output and NOT for this one** (`.url` on Windows, `.webloc` on macOS). Everything goes through `kind_extension` / `kind_extensions` / `kind_from_path`. `make_recorder` in particular must not strip the suffix: a `.webloc` recorded as kind `webloc` answers a question nothing asks while the `url` row the analyzer wants reads as missing for ever. `kind_extensions` lists the other platform's suffix too, so a folder first synced on Windows is adopted on a Mac rather than duplicated.
- **A produced shortcut carries a source marker, and that marker is all that stands between it and `converters/url.py`**, which compiles every shortcut in a course folder into `Compiled_External_Links.txt` and then DELETES it. Without it the selected output is destroyed on every run and restored by the next sync, endlessly. The marker is a `[CanvasDownloader]` INI section (`.url`) or a sibling plist key (`.webloc`) - both ignored by the shell/Finder - and it lives in the file rather than in a manifest so it works in download mode, in sync mode, and in a folder whose manifest seed write failed. `shared/shortcuts.py` owns the format for all three consumers; `write_shortcut` strips newlines from the URL so Canvas-controlled data cannot open its own section and mark itself exempt.
- **A shortcut needs NO Panopto session, and that is the whole economy of the feature.** Discovery already performs the LTI launches, so `PanoptoVideo.panopto_host` is captured for free (`panopto/auth.py:extract_panopto_host`, whose host class excludes `/` - a lazy one matches from the FIRST scheme in a Canvas `retrieve?url=` link and yields a plausible-looking URL that points nowhere). The runner skips its per-course bootstrap entirely when nothing but links is wanted, so a course whose LTI chain is dead still gets its links. Verified live: 36 links, **0 runner handshakes**.
- **The Canvas module-item fallback is valid ONLY for `source == "module"`.** A `source="folder"` recording carries the item id of whichever module item's launch enumerated the folder - use it there and every recording in the course points at the SAME lecture, thirty shortcuts, one destination, no error anywhere.
- **Default OFF**, unlike mp3/txt/srt: the key did not exist before, so every stored contract answers False, and a True default would write a new file beside every recording in every folder the app has ever synced on the first run after an update.
- `panopto.settings.contract_from_ui_state` is now the ONE reader of the `persistent_pan_out_*` toggles - it replaced five hand-written copies (app.py, sync_ui.py x2, sync/analysis.py, ui/sync_dialogs.py), any one of which could have been missed with no symptom but a format the user selected never being produced.
- **macOS is the same feature in the other file format**, and every difference is downstream of one function (`shortcut_extension`). Verified by making `platform.system()` answer `"Darwin"` and driving the real runner: `.webloc` written, valid two-key plist (`URL` + the marker - Finder reads the first and ignores the second), recorded as kind `url`, the identical Canvas-link collision resolved to `<title> (Panopto).webloc`, the URL compiler's `*.webloc` glob sparing ours, and a Windows-synced folder's `.url` files adopted rather than duplicated. **What that cannot prove is Finder itself** - but `_create_link` has shipped the identical `plistlib.dumps({'URL': ...})` form on macOS for as long as external links have existed, so the only new thing on disk is one extra plist key. Nothing else is platform-gated: `make_long_path` returns its argument unchanged off Windows, and the mac spec bundles `assets/`, `shared/` and `panopto/` wholesale.
- Covered by `tests/test_panopto_shortcut.py`; all **27** mutations of the real code are caught (two of them macOS-only), so re-run the mutation pass rather than just the suite.

### ...and the ownership rule was two-sided, written ONCE (2026-08-22)
`resolve_shortcut_path` is careful: it adopts a shortcut we produced and steps over anything foreign, with a docstring explaining that overwriting is not the fix because *"two subsystems taking turns clobbering one path, for ever"*. **`core/canvas_logic._create_link` had no ownership check at all** - a Panopto lecture IS a Canvas ExternalTool item, so in the *match* layout the two compute the SAME path.
- **Measured on the real `.canvas_sync.db` of course 43660**: **36 paths present in BOTH `sync_manifest` and `panopto_manifest`** - precisely the state the design exists to prevent. Plus 5 `.webloc` rows whose file is genuinely gone (real external links; the existing bypass covers those).
- **The chain is an ORDERING one and none of it is adoption**: `_create_link` writes all 41 links and records a row hashing each -> post-processing's URL compiler compiles and DELETES all 41 (they carry no marker - `_create_link` writes a bare `plistlib.dumps({'URL': url})` and never calls `write_shortcut`) -> the Panopto pass finds the names FREE and writes its own marked shortcut there. Confirmed by `app.py:1812` -> `:1863`.
- **The register recorded the opposite mechanism** ("adoption happened, because write_shortcut marked it") and therefore called it a harmless stale md5. `is_produced_shortcut` answers **False** for `_create_link`'s output - one direct test of the predicate disproves it. **A finding's stated mechanism is a hypothesis; test the predicate it rests on before building on it.**
- **It is not a bookkeeping wart**: `_create_link` overwrites the user's SELECTED Panopto output on the next run, and survived only because the compiler deleted it again and Panopto rewrote it - correctness resting on an unrelated converter toggle. Cancel the Panopto pass mid-run and the shortcut is gone.
- **Both halves, because the file layout is right and the bookkeeping is not.** `_create_link` skips writing over a produced shortcut - and **still records the manifest row**, or the Canvas item has none, reads as NEW on every later sync and is re-offered for ever; recording also re-hashes what is on disk, which heals folders built before the fix. `analyze_course` gains the SECOND FORM of the URL Compiler bypass: a row whose file was **REPLACED** by a produced shortcut is up to date, exactly as one whose file is **GONE** already is. Without it all 36 classify `modified` on the md5 check, so the first Canvas-side edit to any of those module items forks a `_NewVersion` sibling for a file the user never touched.
- **A census test, not a spot check**, because this is the shape the repo keeps hitting (a fix landing on two of three delete sites, one of two twins, five of six call sites). It resolves the CALL through the **AST**: `from shared.shortcuts import is_produced_shortcut` keeps the name in the file after the guard using it is deleted, so a name-grep passes against code with no check left - and there is a mutant that proves it.
- `tests/test_shortcut_ownership.py` (15); `scripts/_mutate_shortcut_ownership.py` **9/9**. Two survived the first pass and both were real gaps: nothing had ever driven the ownership check **raising**, in either place.

### A guard added to CI and never dispatched is worse than no guard (2026-08-22)
`scripts/check_macos_floor.py` went in on 2026-08-14 wired straight into `build-macos.yml`, with no test. The last successful macOS build was **2026-07-11**, so its first ever execution was 2026-08-22 - where it failed the v2.0.2 build claiming the bundle *"requires macOS 1267.0"*, with 214 of 215 binaries over the floor.
- **1267.0 is ld64's version.** `LC_BUILD_VERSION` carries the linker's version in a field literally named `version`, four lines under the `minos` the script wanted: `platform 1 / minos 11.0 / sdk 26.5 / ntools 1 / tool 3 / version 1267.0`. A line-wise `minos|version` regex matches it on every modern binary. `LC_SOURCE_VERSION` and `LC_LOAD_DYLIB`'s `current version` are the same hazard in milder form.
- **The floor had not moved**: the real maximum is **14.0**, exactly what the spec declares and the website promises. In the BUNDLE the driver is `libonnxruntime`, not PyAV - `av` is excluded by the FFmpeg-twice fix - so measuring the venv and measuring the bundle give the same number for different reasons.
- **The parser now tracks which load command it is inside** and reads `minos` only under `LC_BUILD_VERSION` (and only `platform 1`; a MACCATALYST minos is a different OS's numbering) and `version` only under `LC_VERSION_MIN_MACOSX`.
- **An implausible parse returns exit 2, "could not inspect", naming the value** - not a build failure. A four-digit macOS version is a parse bug, and a guard whose whole job is honesty must not block a release on a number it does not understand.
- The tests are deliberately platform-independent (pure text for the parser, an injected `minos_reader` for the decision) so they run on Windows too. **The same discipline is why `scripts/build_windows.py` deliberately does NOT read the PE resource back out of the built exe** - that guard can only be tested on Windows, and it was hardened on a Mac.

### The Windows build had TWO implementations and one was wrong three ways (2026-08-22)
`scripts/build_windows.ps1` ran a bare `pyinstaller` (so `version_info.py` - generated AND checked in - was never regenerated), called `iscc` with **no `/DAppVersion`** so the `.iss` fell back to a hardcoded `2.0.0` and produced `Canvas_Downloader_Setup_2.0.0.exe` on a 2.0.2 tree, and then printed the path of a 2.0.2 file it had not created. None of that is visible from reading either script; it is visible from **noticing there were two**. It now delegates and owns no logic. The `.iss` `#error`s instead of defaulting.
- `build_windows.py` verifies every artifact it produces, treats a missing ISCC as an ERROR rather than printing "built successfully", and **emits the release asset name itself** (`Canvas_Downloader_v<ver>_Windows.exe`) so the manual rename - which `marketing/FINDINGS.md` records shipping wrong on v2.0.1 - cannot be got wrong. A test pins the coupling that would fail silently: the emitted name must match the pattern `sync_release_page.py` uses to FIND the Windows download.

### "Shipped version" must mean the same thing to all THREE consumers (2026-08-22)
`ui/update_banner.py` asks `/releases/latest` (excludes prereleases), `scripts/sync_release_page.py` skips `prerelease`, and the two website/version guards used a bare `git tag`. Publishing v2.0.2 as a **prerelease** (macOS DMG only, Windows still building) turned six guards red against a repo that was correct - and obeying them would have pointed the site's Windows button at an asset that does not exist. `sync_release_page.newest_shipped_version()` is now the single definition.
- **`test_version_leads_tags` relaxed from strictly-ahead to NEVER-BEHIND**, and the evidence was already in the file: its sibling asserts the real harm through the real `_is_newer` and **passes** at `version.py == newest tag`. Strictly-ahead is also unsatisfiable during the release window - a release is finished when its installers are attached, not when it is tagged, and bumping at tag time makes the next Windows build stamp the wrong version into the installer that has to hang on it. **Bump `version.py` when you START the next version.**

## The global Panopto switch: STORED contract vs EFFECTIVE contract (2026-08-09)
`panopto_globally_enabled` shipped as an almost entirely **cosmetic** setting. It had exactly two readers - `shared/legal.py` and the Settings dialog - and neither sat on an execution path, so switching Panopto off left Custom Download's Card 4 fetching every selected output, left three of the five Quick Download presets fetching recordings, and left the sync page running the **full discovery pass** and downloading. Only the Today daily sync honoured it, and only because `core/auto_sync.py` sets the run-scoped decline flag for an unrelated reason. Meanwhile `require_panopto_notice` logged *"Panopto skipped: turned off in Settings"* and **returned True so the run proceeded unchanged** - the log line was the only thing in the app that claimed a skip. Two pieces of shipped copy already specified the missing behaviour (`ui/auth.py`'s *"Off means: no institution lookup, no discovery, no acceptable-use dialog, and no recordings in any download or sync"*, and the toggle's own tooltip), so this was a bug whose spec was written in a comment directly above the control.
- **The fix is one named distinction, and it is the whole design.** A folder's `panopto_contract`, a preset's `pan_out_*` and Section 4's session toggles are all **STORED** - statements about what the user CONFIGURED, and what every display surface must keep reading. `panopto.settings.effective_contract(stored)` applies the switch and is what every execution entry point resolves through. Conflating the two is exactly why the switch had nowhere to land: `is_enabled(stored)` was the only gate.
- **Turning Panopto off is a statement about the FUTURE, never a rewrite of the past.** Nothing mutates: a folder's stored contract survives untouched and the user's Card 4 selections are not zeroed, so switching back on resumes recordings with the outputs originally chosen. `effective_contract` returns a value and performs **no write** - asserted with an `open`/`os.replace` spy, because a mutant that re-persisted the settings produced a **byte-identical file** and a content comparison saw nothing.
- **WHERE the gate goes is load-bearing, not a style choice - and the obvious placement is destructive.** The download-mode phase seeds each folder's `panopto_contract` (`app.py`, "Persist this run's contract") **before** it calls the batch, and `sync_ui` only ever seeds `if ... is None`, so a download run is the one thing that can overwrite it. A "one guard at the bottom, nothing can bypass it" gate inside `panopto/runner.py` would therefore let the phase start, write an **all-off contract over every folder it touched**, and turn a reversible preference into permanent per-folder data loss that nothing would restore. The gate is at `app.py:_next_phase_after_courses` (above the seed), `sync/analysis.py` (above discovery), and `sync_ui.py:_run_sync_panopto` as a **logged** backstop only.
- **It must NOT be folded into `compose_settings` or `is_enabled`.** `extract_contract` seeds from the first, so the switch reaching in there is the same data-loss bug by another route; the second is asked by DISPLAY code - the sync hub's stored config, the preset cards, and the ignored-recordings dialog's "which kinds count as configured" - so making it switch-aware reports that a folder set up for recordings never was.
- **In sync mode the switch skips the WORK, not just the result.** `sync/analysis.py` reads it directly into `_pan_on` before anything else: no stored-contract read, no manifest heal (which **writes**), no discovery. That is where the switch is worth the most - discovery is a per-recording LTI handshake, and at a university with no Panopto it is ~48 handshakes at 1-2s each that can only ever return nothing. `panopto_payload` stays `None`, already the documented shape for "the feature is disabled", so every consumer downstream needs no change.
- **`_pan = compose_settings(...)` moved INSIDE the gated branch**, so every read of it must be too - and this module swallows the whole Panopto block in a bare `except Exception`, so a stray read would surface as a logged warning and a silently absent payload, never a traceback. Same shape as the `isolate` bug in `core/canvas_logic.py`. Pinned by an AST test, not by reading.
- The two sync-page pair helpers short-circuit **before** their per-pair loop, which is both the honest answer and much cheaper: they run on every sync-page render and open a `SyncManager` per pair, so the switch replaces N SQLite connections with one config read.
- Covered by `tests/test_panopto_global_switch.py`; all **20** mutations of the real code are caught, so re-run the mutation pass rather than just the suite. Four of those mutants escaped a first, substring-based version of the tests purely because `from panopto.settings import is_globally_enabled` keeps the NAME in a function body after the guard using it is deleted - match the **call** via AST, and reject a test weakened into a compound (`if False and not ...`).

### The same switch, Pass 2: what the SURFACES do about it
**One rule decides every case: OFFER vs RECORD.** A surface that OFFERS Panopto (a control that would cause a recording to be fetched) goes unavailable. A surface that RECORDS it (a stored contract, a completion screen, sync history) is NEVER rewritten - it is a statement of fact about how something is configured, and that stays true while the switch is off - so it gets ANNOTATED instead. The seductive wrong turn is "the run skips it, so make the config viewer say *None selected*": that reports a folder set up for recordings as one that never was, and the pills reappear the moment the switch goes back on. Covered by `tests/test_panopto_switch_ui.py`; all **25** mutations caught.
- **Card 4 is DIMMED, never removed** (`ui/download_settings.py:_render_card_panopto_off`). Removing it leaves the download page with no mention of Panopto at all, so a user who switched it off weeks ago has no route back from the screen where they would look - the "a disabled control must say why" rule, whose whole point is that hiding the reason turns an unavailable thing into a dead end. It also keeps the big help card's "Card 4" section from documenting something absent. The off-state emits the **same three children as the collapsed on-state** (style / icon / header row) because Streamlit reconciles by position, and it keeps the header to ONE line because the row's geometry (`margin-top: -35px`, the icon at `top: -24px`) is tuned for one - the message rides in the TAG, reusing the on-state's own `OFF | <detail>` idiom. Two keys (`card_panopto` / `card_panopto_off`), the `stg_card_pan_off` trick, because a container carries no attributes; `st-key-card_panopto_off` still contains `st-key-card_panopto`, so the shared `[class*=]` card chrome applies unchanged.
- **Dimming is the app's ONE disabled recipe and nothing on top** - `brightness(0.5) saturate(0.5)`, plus `filter: none` on any disabled button INSIDE a dimmed card, because filter multiplies through nested elements and the shared `button[disabled]` rule would compound with the card's. A "50% opacity + 50% saturation" treatment was proposed and declined for exactly the reasons in "Disabled buttons: ONE recipe" - opacity multiplies, a second `filter` replaces.
- **The config viewers annotate once per COLUMN**, not per pill (`shared/components.py:render_config_summary_badges`): the pills stay, dimmed, under one "Won't run - Panopto is off in Settings" line. Five "won't run" badges say nothing five times. Nothing is annotated while the switch is on, or when the column has no outputs (that would put a notice on the majority of presets).
- **The skipped-recordings report is the THIRD member of an existing family**, not a new component - `shared/components.py:render_panopto_disabled_notice`, beside the size-skip and unpacked-archive panels, sharing `.skip-panel.skip-panel-solo` and its CSS verbatim. **It counts COURSES, not recordings, and that is forced by the fix**: switching Panopto off skips discovery, so the recording count is genuinely unknown and claiming one would mean running the very scan the switch avoids. The courses are resolved AT RENDER from each folder's stored contract (a cheap local read) - nothing is plumbed through the engine, so it cannot go stale.
  - **Its icon must be FILLED, and `fill-rule: evenodd` is a trap here.** The first film strip carried an inner `M8 6h8v12H8V6z` subpath, which under evenodd PUNCHES THE CENTRE OUT - the glyph became a hollow frame with a fraction of the ink of the solid funnel and archive box beside it, i.e. exactly the "reads as an element of a different family" failure the icon block's own comment warns about. Invisible in review and in the DOM; found by screenshotting the three panels together at **4x device scale** in the real gallery. Do that whenever adding a member.
- **Today gets its own line, never `skipped`** (`core/auto_sync.build_today_sync_notice` -> `panopto_off`). That field means "the folder is gone, go fix it"; this means "working exactly as you configured it". One needs an action, the other needs none, so merging them misreports both. It matters most here: the daily sync is the run nobody watches.
- **The transcription dialog stays reachable while a model or the CUDA libraries are installed**, relabelled "Manage installed models". It is the ONLY place either can be deleted and they run to multiple GB, so dimming it with them installed stranded that disk space behind a switch-on / delete / switch-off dance nobody discovers. "The engine is a SUBORDINATE of the master switch" was always about not offering to CONFIGURE a feature that cannot run - never about trapping the user's disk.
- `scripts/completion_gallery.py` carries a `d-panopto-off` variant rendering all three family panels together, which is how the icon defect above was found. The gallery runs with `--server.fileWatcherType none`, so **restart it after editing a module constant** - an edited SVG will otherwise render as the old one and read as "my fix did nothing".

### The transcription-setup notice is DISMISSIBLE on the sync list and nowhere else (2026-08-19)
The amber "Transcripts & Subtitles need a one-time setup" card re-rendered on **every** render of the sync page, for ever, with no way to close it. That is a fair report of a STANDING mismatch - the folder's stored `panopto_contract` asks for txt/srt and the next sync will silently not produce them - but every way out of it was heavy: install a model, switch Panopto off globally, or **re-download the whole course** with the outputs unticked. A folder's `panopto_contract` is written by the download flow (`app.py`) and seeded on first sync; the hub, the sync dialogs and the config viewer only READ it, so there is no UI that edits it. The user had no proportionate answer at all.

The flag is persisted (`panopto.settings.TX_NOTICE_DISMISSED_KEY`, top-level beside `panopto_globally_enabled`): session-only still nags once per launch, which is the same complaint.

The sync REVIEW notice is an EVENT report about the run in front of you ("N pending recordings are set to produce Transcript or Subtitle files"), seen once per analysis at the last checkpoint before the run starts - it keeps the full card whatever the stored flag says. A shared flag makes hiding it there easy and it is the worst place to hide it.
- **The stylesheet MOVED to `styles/global.css`, and that is a correctness requirement.** It was an inline `st.html(<style>)` inside the function, i.e. emitted only in the branch where the notice renders - and this notice now has a branch that flips **on a click, mid-session**, which is precisely the conditional-stylesheet bug (style hosts reconcile BY INDEX, so a branch flip shifts every LATER stylesheet onto its neighbour's host). Selectors are prefix-based (`st-key-tx_setup_card_` / `_btn_` / `_close_` / `_link_` / `_relink_`) so one rule covers both surfaces, and `inject_css()` puts them in the MAIN container where no fragment rerun can reach them. - **Both branches emit `_TX_NOTICE_SLOT_CHILDREN` (2) children**, padded with `pad_slot_children`, because they render at the same index and `addBlock` hands a new block the CHILDREN of whatever sat there. The collapsed slot sets `gap: 0` - a blank child is zero-HEIGHT, not zero-COST.

The READ deliberately stays inline in each writer - that is the half `tests/test_settings_coownership.py` asserts per writer, and folding it in would make that census stop measuring anything. ### A conditional `<style>` really does shift the EVENT host list - MEASURED, and three sites still had it (2026-08-20)
The rule above ("NEVER emit a `<style>` block CONDITIONALLY") was documented as Critical and **gated for the dialog variant only** (Rule 9). A whole-project sweep found **15 sites with the shape**; three were live and are fixed. Found by asking the self-critique question after the transcription notice landed - that change *armed* a latent instance, because its branch now flips on a click.
- **THE DIAGNOSTIC, and it is the reusable part**: sample `[data-testid="stEvent"] [data-testid="stHtml"]` in document order on every animation frame, then diff **by index** rather than by set. A missing stylesheet is invisible in a set comparison; a *displaced* one is the whole bug. Recorded across a real "Analyze, Review & Sync" on the sync page:

  | | |
  |---|---|
  | at rest | 5 hosts; `[2]` = the page's **277KB** main stylesheet, `[3]` hub button, `[4]` main-column buttons |
  | **t=+242ms** | `[2]` **REWRITTEN** with the sidebar's run-lock stylesheet; the 277KB sheet gone from the list entirely, while `[3]` and `[4]` still held the **previous screen's** stylesheets |
  | t=+288ms | settled |

  Index `[2]` held **three different stylesheets during one run**, index `[3]` three. After the fix the sidebar's sheets sit at fixed indices in every frame and no index is ever handed a stranger's sheet - the only remaining churn is a main-page sheet replaced by another main-page sheet when the screen genuinely changes, which is what reconciliation is for.
- **The event list is SMALL, so the blast radius is not "every stylesheet on the page"** - measured on the sync page: **5 hosts in `stEvent` against 10 style-bearing containers in `stMain`**, because `inject_css()` uses `st.markdown` (MAIN container) and only style-ONLY `st.html` is routed to the event root. Correct the instinct before sizing a fix.
- **All three sidebar guards were SELF-GATING, and that is what makes deleting them safe rather than a trade.** Every rule in the two lock blocks is scoped to `button:disabled`, and those buttons carry `disabled=_locked` / `disabled=_is_executing`; the active-nav block keys off `st-key-nav_btn_{mode}`, which matches nothing for a mode with no such button. So the `if` never changed what the page *looked* like - it only moved index boundaries, and **the sidebar renders BEFORE the main page**, so those boundaries sit ahead of every main-page sheet. Verified mid-run in the real app afterwards: Download/Today/logout dimmed at `brightness(0.5) saturate(0.5)` with `cursor: not-allowed` and the RUNNING mode's button at `filter: none` - the "you are here, and it's running" exclusion still fires - and the sidebar is pixel-identical at rest.
- **The course list was the fix landing on one of two twins.** `_render_multi_select_list` carries a comment saying its own `if combined_css:` was *"safe only by accident"*; `_render_single_select_list` still had it **and** nested the first row's `margin-top` inside the same guard - so a list whose courses carry no parenthetical code lost its `-10px` alignment *and* shifted the host list, in the same branch. Both now mirror each other exactly.
- **A test that guards one of two identical twins is the same defect one level up - and the mutation pass proved it on my own test.** After the fix the two renderers are textually identical from `boundary_css = []` onward, so the mutant's anchor matched **twice**, `replace(..., 1)` silently mutated the *multi*-select, and the run reported SURVIVED while the label said single-select. Anchor uniquely (include a preceding line) **and** parametrize the test over both twins.
- **`_is_style_only` is the ROUTING rule and it decides WHICH bug you have**, so classify before fixing: nothing but style tags and comments left over → the EVENT root container, one global index-addressed list (this class); one byte of real content beside the style tag → the MAIN container at the call site's own delta path, where a conditional emission is the **container-inheritance** hazard instead, local to its own parent. `ui/auth.py`'s `if display_user:` block is the second kind and is deliberately left alone.
- **12 further sites match the shape and were triaged, not fixed.** The question that separates them is *"can this branch flip while the rest of the page stays stable?"* - none of the twelve can; each either cannot flip in a session (the completion-card variants, the preset icon's base64 load) or flips together with a full screen replacement (sync history, sync review, hub layers). An audit **Rule 11** was considered and DEFERRED: it would need each of the twelve justified or suppressed, which is a separate piece of work with its own churn.
- Covered by `tests/test_conditional_stylesheets.py` (8); all **9** mutations caught (`scripts/_mutate_conditional_styles.py`), so re-run the mutation pass rather than just the suite.
