01What the backend is now

Three ways in, one credential. Nothing below the auth layer can tell them apart, because core/canvas_auth.py is the only place a bearer header is formatted and the credential VALUE carries the answer. All thirteen CanvasManager construction sites are unchanged.

The straight path Sign in with Canvas core/browser_login.py

A second app window opens on the school's own login page. The student signs in the way they always do. The app harvests the session cookies and uses them exactly as it would a token.

Where tokens still work Minted access token core/token_mint.py

Straight after a sign-in, the session is spent on a long-lived token. The student never sees Canvas settings, never copies a string. Silently skipped where the school has switched token creation off.

Supplementary Browser extension handoff core/handoff.py + extension/

One click in Chrome on a Canvas tab that is already signed in. Nothing typed, no school picked, no password entered, because the browser already did all three.

02How it keeps the student signed in

This was the number one ask: a login screen on every launch is what kills retention. Four mechanisms, in the order they take effect.

MechanismWhat it doesLives in
A profile that survives the session pywebview defaults to private_mode=True, which runs the web view InPrivate against a temp folder thrown away on exit. Turned off, with an explicit storage_path, so the web view keeps cookies and site data between launches. start.py
Session cookies re-dated to 30 days The profile keeps a cookie with an expiry date and loses one without. Every relevant cookie, the school's identity-provider one included, is re-dated in place through AddOrUpdateCookie after a successful sign-in. browser_login.persist_session_cookies
The password manager, switched on The sign-in window offers to save the institution password and to autofill it next time, so a re-login is a click rather than typing a university password. Read back after writing, so a build where the setting does not take is reported rather than assumed. browser_login.enable_password_manager
A minted token, renewed early 119 days requested against Canvas' 120-day ceiling. The grant is whatever the school allows, so renewal fires at min(21 days, granted / 3) rather than a fixed window. core/token_mint.py

The per-institution expiry was a real bug, caught by your own correction. A fixed 21-day renewal window made a token from a school granting 7 days due for renewal the instant it was minted. It now scales with the grant.

04Found today: two framing bugs in the handoff listener

Both were on the extension's live path. Both were invisible to thirty existing tests, for one reason: urllib opens a connection per request, so an unread body is followed by end-of-file and the server never trips over it. A browser does the opposite. It keeps the connection and sends the next request down it, which is exactly the pair the extension makes.

A refused request poisoned the next one on the same connection

core/handoff.py · found by building the dev harness · fixed

Every refusal answered without reading the request body. The connection is keep-alive, so those bytes were still in the socket when the server went looking for the next request line, and it read the tail of a JSON body as a request.

with the drain removed          (positive control)
  1st: HTTP/1.1 403 Forbidden
  2nd: HTTP/1.1 501 Unsupported method ('{"host":"x","cookies":{}}GET')

fixed
  1st: HTTP/1.1 403 Forbidden
  2nd: HTTP/1.1 200 OK

The second request is the extension's own POST /canvas-session, arriving after the GET /ping it uses to find the port. A handoff that cannot land, on a connection the browser is entitled to reuse.

The CORS preflight returned a body with a 204

core/handoff.py · RFC 9110 violation · fixed

A 204 response is terminated by the end of the header section. It cannot carry a Content-Length, so a client that knows the rule does not read the two bytes of {} we were sending, and they sat in the socket. Chrome sends this preflight before every handoff POST, because Content-Type: application/json is not CORS-safelisted.

with the body restored          (positive control)
  status         204
  Content-Length 2
  body bytes     0
  traceback      YES  (ConnectionResetError)

fixed
  status         204
  Content-Length (absent)
  body bytes     0
  traceback      no

Two smaller things fixed alongside them

core/handoff.py · hardening

  • Handler failures went to stderr as tracebacks. This listener silences its own logging precisely so it never writes there, and a windowed Windows build has no stderr at all. A dropped connection is now logged at debug and anything else at warning, rather than printed or swallowed.
  • Idle keep-alive connections held a thread each. A ten-second handler timeout closes them, so nothing can pile threads up by connecting and saying nothing.

How they were found matters more than what they were. Neither came from reading the code. Both came from building the harness you asked for and looking at what the listener actually put on the wire. The first sign of them was a stray traceback in terminal output that a less suspicious reading would have dismissed as noise.

05The md5 finding: it does not reproduce

add_file_to_manifest is correct as written

core/sync_manager.py:2701 · flagged 2026-09-11 · investigated and closed

I flagged this as needing a look because it hashes the file on disk unconditionally and writes the result as original_md5, which is the same shape as the data-loss defect fixed in its sibling record_downloaded_file on 2026-08-20. original_md5 is the sole basis of edit protection, so a baseline taken from the student's edited file is what turns a protected file into an overwritable one.

Reachability is what settles it, and reachability is what I had not established. The function has exactly two call sites, both in sync/execution.py:

  • Line 1128, the real file download, passes local_md5=_dl_hasher.hexdigest(): the bytes just pulled off the network. The on-disk hash never runs.
  • Line 1735, the synthetic shortcut and Canvas Page path, passes nothing. Every route to it writes the file immediately beforehand: the real page HTML, or the redirect stub, or the .url shortcut. A path with nothing to write hits continue and never reaches the call.

So the unconditional hash is always hashing bytes the app itself has just written, which is the correct baseline. This is the same distinction that made the sibling's fix correct: hashing is right when the file is ours, and wrong when we are re-recording a file that was merely found on disk.

What is actually worth doing about it

residual risk · the invariant is stated but not enforced

The docstring claims the caller contract ("this is always a fresh-byte download") and nothing checks it. That is exactly how the sibling acquired its bug: a third caller was added later that recorded skipped-but-existing files, and the docstring was still true of the two original ones.

A census test that fails on a new, unclassified call site is the cheap guard, and it is this repo's own stated pattern for a fix of this class. It is worth adding; it is not urgent, because nothing is currently wrong.

06Dev testing, which now works

streamlit run app.py cannot open the sign-in window and never could. The window is a second pywebview window, and pywebview only creates one once webview.start() has run on the process's main thread. Under streamlit run, Streamlit owns that thread, no GUI loop ever starts, and the button correctly refuses.

Is it the real thing? Yes, and here is what that rests on

asked directly · enforced by tests/test_dev_tooling.py

You asked whether I built something that imitates the auth screen. I did not, and the answer should not depend on my word for it, so it is now a test.

dev.py contains exactly one page of its own: a three-row status panel. The app is the real app.py, served by the real Streamlit server, started through start.py's own _launch_streamlit - production's function, not a copy. Every module under test is the shipped one, in a single process.

What the test forbidsWhy it would matter

One thing genuinely differs, and it is the rendering surface

use --window for anything about layout

By default the app is drawn by your browser; the shipped app draws it in WebView2 (WKWebView on macOS). Functionally that is nothing: both are Chromium on Windows, and there is no window.pywebview or js_api call anywhere in the app - I checked, and inject_app_shell_bridge is pure DOM JavaScript. But layout is not a functional question, so --window loads the app into the pywebview window instead, in the same engine the shipped build uses. Use that for the auth-screen work. python start.py is production-faithful too, and always was; what it cannot give you is DevTools and a live DOM.

And one pre-existing difference from the installed build, which is not this file's doing: run from source the config dir is the repo root, so the profile is <repo>/webview rather than %APPDATA%. python start.py has always behaved the same way. So signing in here does not sign you in inside the installed .exe, and the two cannot fight over the same WebView2 profile lock.

Does the dev run talk to the extension?

Yes, and it always did. The listener is a thread in whichever process runs the app, with no dependency on pywebview, so it works under streamlit run app.py too. What was missing was any way to see that without Chrome in the loop. check_handoff.py runs ten checks against the live listener using the app's own port and cookie constants, so it cannot drift by probing somewhere the app is not listening. Nothing consumes the arming by default, so the real extension can be tested on the same arming straight afterwards.

The end-to-end script

  • python dev.py, and read the banner. If the sign-in line says NOT available, the GUI loop did not come up and every sign-in test after it is void.
  • Press Sign in with Canvas and finish a real CBS sign-in. The terminal prints the mint's verdict, the harvest and the sign-in state as they happen.
  • Close the dev host, run it again, and see whether you land signed in. That is the retention claim, and nothing else substitutes for it.
  • Press the extension card, then run check_handoff.py in a second terminal. Green means everything but Chrome is right.
  • Then for real: load extension/ unpacked at chrome://extensions with Developer mode on, open a Canvas tab, click the toolbar button.

07Not verified, and needing you

Every item here needs a human at a real institution login. None of it can be faked, and none of it is asserted anywhere as working.

  • The mint against real CBS Canvas Expected to be refused, because CBS has token creation switched off. What matters is the exact refusal, so the code classifies it as permanent rather than retrying for ever.
  • Whether Entra's "Stay signed in?" prompt renders in the web view This is the single most load-bearing interaction in the feature. Ticked, the app can renew itself for weeks. If the prompt does not appear at all inside the web view, the 30-day story rests only on our own re-dating.
  • The password save and autofill round trip Nothing in a test can click a browser's own save prompt. The setting is verified as written and read back; that it results in a filled password is not.
  • Sign in, close, reopen a day later, land signed in The actual retention claim. Canvas' own session is about a day, so the test only means something across one.
  • The handoff through real Chrome to a real Canvas tab The extension loads now, and the app side is proven by the checker. What is untested is Chrome's half: the permission prompt, the httpOnly cookie read, and the preflight that the 204 bug was sitting on.
  • macOS, entirely Every measurement in this document is Windows. The web view there is WKWebView, not WebView2, and the cookie re-dating and password-manager code are both WebView2-specific by construction.

08The auth screen, diagnosed rather than described

You said the layout looks horrendous and that I followed the rules about emitting a Streamlit button without considering the design. That is accurate. Here is the specific reading, taken off the real screen in the dev host, so the redesign starts from a diagnosis instead of an adjective.

#What is on screenWhy it is wrong
1 The two sign-in routes are outline buttons. The token route's Log In is solid primary blue. The weight is exactly inverted. The route you want a student to take reads as the secondary option, and the dead end for a token-disabled school is the most prominent control on the card.
2 Get a token is also solid blue. Two competing solid buttons in the lower half, none in the upper half. Nothing on the card reads as "start here".
3 Two full-width outline buttons, stacked, identical weight. They read as a pair of equals, so nothing distinguishes the straight path from the supplementary one. The extension is meant to be an add-on and looks like a co-headline.
4 Three lines of small grey hint text interleaved between the buttons. The stack reads as prose with controls buried in it rather than as a choice between routes.
5 The card is about 930px wide. Too wide for a form this simple, which stretches every full-width button into a slab and makes the vertical stack feel longer than it is.
6 Spacing runs field, tight gap, button, hint, button, hint, divider. No consistent vertical rhythm, so nothing groups. Each control looks equally related to everything around it.

I have not touched any of it. You said you would give a reference and tell me exactly how it should look, and guessing twice costs more than waiting once. The one thing I would flag as a decision rather than a taste question is #1: whichever direction the reference goes, the solid-primary weight should sit on the route most students can actually complete.

09Queued, and deliberately not started

  • The extension's copy and its store presence. It reads as though the student already knows what to do, and it names a button that does not exist: the popup says press "Use my browser" while the app's button says "Use the Canvas tab in my browser". That is a factual error in user-facing copy, not a style preference. Being rewritten for a non-technical student, with the listing text a store page needs.
  • A visible control for "stay signed in". The setting is read and honoured, and nothing in the interface flips it. Placing it needs a browser-verified pass, because Streamlit reconciles by index and a control that comes and goes hands the next element its DOM node.
  • The single-sign-on pop-up gap. Fixable with pywebview's OPEN_EXTERNAL_LINKS_IN_BROWSER, which is process-global, so it can only be flipped while a sign-in window is open. Not implemented.
  • Store listings for the extension. Not set up. Install is Developer-mode only, which is why the app never assumes the extension is present and never implies it is required.
