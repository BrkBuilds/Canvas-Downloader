Sign-In: Security, Robustness and Token Parity

A second pass over the browser-session login, one day after the audit that shipped it. Three questions: can it be made safer, can it be made harder to break, and does a user who signs in get the same app as a user who pastes an access token.

date 2026-09-12
tree uncommitted, main
suite 4,591 passed · 0 failed
mutation 50/51 (survivor documented)

Parity is close, and the two remaining gaps are known and bounded. Panopto, which was the blocker yesterday, now takes the in-app LTI launch and works. Downloads, sync, the course cache, logout, reconnect and the optimistic offline restore all run through the same code for both credentials. What a browser session still does not give you is a verifier= on file URLs embedded in exported HTML pages, and a credential that lasts as long as a token does.

Seven defects found and fixed, three of which are security-relevant. The most interesting is not a bug in the new code at all: trimming the harvest to fit the Windows credential store also stripped the WAF clearance cookie off the live session, so an institution behind a Cloudflare challenge would have been told its session had expired, with nothing it could do about that.

The largest remaining security item is not in this app. A harvested Canvas session cannot be revoked by the user the way an access token can. That is stated below rather than fixed, because fixing it needs a measurement against a live authenticated session that this pass could not take.

Guard
G-01

The full suite caught the one defect the targeted run could not

tests/test_unbound_names.py

tests/test_browser_login.py was green at 101 and the mutation pass was finished; the full suite then failed. The hit was in a guard, not in the product, and it was a false alarm in a file whose docstring promises it never produces one.

A decorator is evaluated in the scope the def sits in, not in the function's own scope. The checker walked ast.iter_child_nodes of the FunctionDef, which includes decorator_list, so @title.setter was checked against the method's scope - where title is of course not bound. The class body binds it two lines above, and a method never sees class-body names, which is exactly the rule that file gets right everywhere else. The first @property / @x.setter pair in this repo's history was written this session, in the new test fakes: a guard is only exercised by the shapes somebody actually writes.

Fix, and the false start inside it. Decorators are now checked against the enclosing body's names, with a class body passing its own bindings down. The first attempt used ast.walk over the decorator expression and reported eleven new false alarms - every one a comprehension variable inside a @pytest.mark.parametrize argument, because a comprehension is its own scope binding its own targets. Two controls were added so the fix cannot have blinded the check: an unbound decorator at module level and one inside a class are both still caught.

Security

Major
S-01

A storage limit was silently narrowing the live credential

core/browser_login.py · core/canvas_auth.py

Yesterday's fix trimmed the harvest to canvas_session because a real CBS credential serialised to 3,260 bytes against Windows Credential Manager's 2,560-byte ceiling, so the whole thing fell through to the DPAPI file instead of the OS vault. That reasoning is correct and the measurement reproduces exactly. But it was applied at the wrong end of the pipe.

The size limit is a fact about the keyring. Applying it at harvest time also threw the extras away for the live session, and one of them can be load-bearing: an institution behind a WAF issues a clearance cookie (Cloudflare's cf_clearance, 426 characters on the measured session). Without it the first API call meets a challenge page - a 200 whose body is not JSON - which verify() reports as "Your Canvas session has expired". At an institution that needs it, that is a login that can never succeed and never says why. The code comment anticipated this and proposed widening the allowlist; a per-WAF allowlist is a list nobody can finish.

Fix. Harvest everything the Canvas host set; trim in to_storable(). The at-rest secret is unchanged and still the smallest thing that authenticates, so nothing is given up: 
full jar (the old harvest)      3260 bytes -> REFUSED (error 1783)
session-only (what is stored)   2018 bytes -> FITS
live in-memory cookies          _csrf_token, canvas_session, cf_clearance, log_session_id
persisted cookies               canvas_session
A restored credential carries the session cookie alone. If that is ever not enough, the request fails the way any expired session does and the silent renewal harvests a fresh complete jar, so the degradation is self-healing rather than terminal.
Major
S-02

On macOS the harvest could adopt another tenant's Canvas session

core/browser_login.py · core/canvas_auth.py

pywebview's two backends do not scope get_cookies() the same way. Windows asks WebView2 for the current URL's cookies and is correct. macOS filters the whole cookie store with a plain substring test:

# pywebview/platforms/cocoa.py
domain = c.domain()[1:] if c.domain().startswith('.') else c.domain()
if domain not in self.url:
    continue

For a window opened on https://cbscanvas.instructure.com/login, a cookie belonging to the unrelated tenant canvas.instructure.com passes that filter, because that string does occur inside the URL. The name allowlist happened to limit the blast radius before; widening the harvest for S-01 would have removed that accident, and the pre-existing hole was already reachable for canvas_session itself - the one cookie that decides the sign-in has finished.

Everything harvested goes into a jar scoped to our Canvas host, which is to say it becomes something the app sends to Canvas. A foreign cookie must not reach it.

Fix. cookie_domain_matches() in core/canvas_auth.py - the browser rule, exact host or a real subdomain, with the dot boundary that stops scanvas.instructure.com counting as a parent of cbscanvas.instructure.com. Applied at the harvest, so both platforms now agree. A morsel with no domain still passes, because that is what a backend which already scoped its query returns.
Major
S-03

The user could not see whose login page they were typing a password into

core/browser_login.py

The address bar is the one thing an embedded web view takes away, and the chain really does leave Canvas: CBS goes to login.microsoftonline.com and back. The window was titled Sign in to Canvas for its whole life, with no URL anywhere on it, so "am I really on my own institution's login page?" was a question a student could not answer. This is the standing objection to embedded-webview SSO and the reason Google blocks it outright.

Fix. The title carries the current origin and follows the redirect chain: Sign in to Canvas - login.microsoftonline.com. Two details are load-bearing:
  • Punycoded. urlparse().hostname returns whatever the URL contained, so an internationalised host arrives in its Unicode form - the form that can be built out of homoglyphs to read as somebody else's domain. A Cyrillic "a" now renders xn--pple-43d.com. Ugly is the correct answer here.
  • It must not block. pywebview's title setter opens with events.loaded.wait(15), and this runs inside the 0.5 s poll loop that owns the harvest, the settle counter and the cancel check. _set_title checks is_set() first. loaded is cleared only by load_url and load_html, never by the redirect chain, so once the first page is in it stays set.
Tracked against the title last applied rather than against the previous URL: the ordinary way the window appears is the settle rule, four polls of an unchanged URL, so "has the URL changed since last poll?" is false on exactly the poll after it is first shown, and the indicator would never have appeared on the common path.

Robustness

Major
R-01

A UTF-8 BOM in the settings file quarantined it and signed the user out

shared/helpers.py and 11 sibling read sites

Carried forward from yesterday's audit as a smaller item; it is worse than it was recorded. A BOM is a legal encoding of the same document, and it is one a human can easily produce - Notepad writes one by default, so does a PowerShell > redirect. Read as utf-8 the BOM survives decoding as a leading U+FEFF and json.load raises JSONDecodeError, which is indistinguishable to the handler from a truncated file. So read_json_for_update did not merely discard the settings, it took the documented corruption path:

WARNING shared.helpers: Config file canvas_downloader_settings.json was unreadable
(JSONDecodeError: Unexpected UTF-8 BOM (decode using utf-8-sig));
moved it to canvas_downloader_settings.corrupt.json

An intact file moved aside and replaced, taking the saved Canvas address, the accepted Panopto notice, the download defaults and auth_method with it - and auth_method is the marker that decides whether a saved browser sign-in is restored at all. This is the "never destroy data on an error you have not identified" rule: corruption must be proven, and a BOM proves nothing.

Fix. utf-8-sig on every JSON read, which handles both forms and is a no-op on a file without a BOM. Twelve sites, all of one class: the shared reader, both direct config reads, the credential fallback reads, the sync-pair store, the library, the presets and the sync history. Writes stay utf-8, pinned by its own test, so nothing starts emitting a BOM.
Minor
R-02

A pending flag with no job reran the app about once a second, for ever

ui/auth.py

Recorded yesterday as reachable in theory and not reproduced. It is a plain control-flow fact: _browser_login_poll treats idle as terminal and calls st.rerun(scope="app"); adopt_pending_browser_login returned on the same idle with the pending flag still set; the next run polls again. The pair is reachable whenever the job is reset by someone other than this session, which is exactly what a second window or a logout in another tab does - the job is process-global and the flag is per session.

Fix. idle is terminal here too and clears the flag. Silently: idle is the absence of an attempt, not a failure that happened to this user, and was_interactive() cannot speak for a job that no longer exists. Pinned by a test that drives the function rather than reading its AST - the old shape passes every structural assertion in that file.
Minor
R-03

A superseded sign-in left its window on screen for its own full clock

core/browser_login.py

begin_login replaced _job and walked away. _finish declines to record a state for a job that is no longer current, so the old worker never reached the branch that closes its window: an already-visible window sat there until its own ten-minute clock expired. Two sign-in windows, one of them for an address the user has moved on from.

Fix. begin_login cancels and destroys the job it supersedes. ui/auth.begin_browser_signin already called reset() first and so covered the app's own route, which is why this never showed up; closing it in the primitive is what stops the next caller rediscovering it.
Minor
R-04

Nothing pinned certificate validation in the sign-in window

start.py (guard added in tests)

No live defect: IGNORE_SSL_ERRORS is False and start.py passes no ssl=, so certificates are validated today. It is written down because the switch is process-global, the same hazard this codebase already documents for private_mode, with a worse consequence. pywebview registers ServerCertificateErrorDetected -> AlwaysAllow when either flag is on, and it would take effect in the Canvas sign-in window as well as the local Streamlit one - the window where a student types a university password, on whatever campus or cafe network they happen to be on.

Fix. A census test asserting both, so a future webview.start(ssl=True) added for the local server fails the suite in the commit that adds it.

Is it 1:1 with the token path?

Everything below the auth layer is genuinely shared: one CanvasCredential, thirteen CanvasManager construction sites unchanged, one _adopt_restored_credential deciding what a network blip means, one force_reauth choosing reconnect copy by credential kind, one auth_method marker written on both login routes. Open, stated rather than fixed

Open
O-01

Signing out of Canvas Downloader does not sign you out of Canvas

Logout deletes the stored credential and wipes the web view's profile, which is the right local behaviour and is verified on Windows. What it cannot do is invalidate the session on Canvas' side, so the harvested canvas_session value stays valid until it expires on its own. A user can revoke an access token from their Canvas settings page; there is no equivalent gesture for a harvested session.

Why this is not fixed here. Canvas' logout is a POST/DELETE that needs the _csrf_token echoed as a header, and whether that actually invalidates a captured cookie depends on how Instructure's session store is configured - which cannot be established without driving it against a live authenticated session. Guessing would put an unmeasured claim in a security-relevant place. The honest statement today is the one above.

Worth noting the exposure is bounded: the value is now in the OS credential vault rather than a file, it is never written to any log the app produces (scanned), and it never leaves the Canvas host.

Open
O-02

refresh_silently() still has no callers

Recorded yesterday as "the function this path wants". The renewal that was wired up instead goes through begin_browser_signin(..., interactive=False) from the login page, which is correct - it must not block the Streamlit script thread. So refresh_silently is 46 lines of tested, unreachable code. It is the natural implementation for a mid-run renewal, which is the one place a browser session is meaningfully weaker than a token: if the session lapses during a long download, the run ends and the user reconnects, where a token would simply have kept working. Either wire it to that or delete it; leaving it is how a future reader assumes the path exists.

Open
O-03

A self-hosted Canvas reached by IP address downloads nothing, silently

Carried forward unfixed. aiohttp.CookieJar() refuses cookies for an IP-address host unless constructed with unsafe=True, and requests' jar refuses them for a dotless host like localhost. Niche, and the safe fix is narrow (the jar only ever holds one host's cookies), but it should be a deliberate decision rather than a discovery.

Verified good, not re-measured

No Authorization header in browser mode Canvas runs load_pseudonym_from_access_token before it looks at the session, so a stray bearer 401s a perfectly good cookie
The cookie never leaves the Canvas host real 4-hop redirect chain: cookies sent to Canvas, none to canvas-user-content.com or either inst-fs host
No credential value in any log the app writes debug_log.txt, health.log, session_state.json and the downloaded folder all scanned
Canvas does not prefix session-authenticated JSON with while(1); 5 live probes, both Accept headers
The sign-in window cannot save or fill a password, and cannot download IsPasswordAutosaveEnabled=false, ALLOW_DOWNLOADS=false, no context menu, no accelerator keys

macOS remains unverified for all of the above. Every primitive used is documented cross-platform pywebview, and S-02 above is specifically a macOS-only hole closed by reading the backend rather than by running it.
