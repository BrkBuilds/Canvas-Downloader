macOS parity: the new sign-in

Where the three ways into Canvas actually stand on macOS, after the first sprint of the browser-based login.

Nothing here has been run on a Mac. Every statement below is read out of pywebview 6.1's own source and this codebase's platform guards. That is enough to say what is missing and what to measure first; it is not a substitute for a machine.

The verdict, one line per route

At parity

Access token

Untouched by this work.

At parity

Use the Canvas tab in my browser (the Chrome extension)

core/handoff.py contains no platform branch at all - standard-library HTTP on loopback, json, threading. The extension is Chrome, which is the same product on macOS. Opening the student's Canvas goes through webbrowser.open. dev.py and check_handoff.py are equally platform-free.

This is the route with nothing left to port. If macOS parity has to be bought cheaply, lead with it.

Behind

Sign in with Canvas (the app's own window)

Three features are Windows-only. None of them fails on macOS; they are silent no-ops, so a Mac simply gets less.

What the app's own sign-in window is missing

All three are guarded with if sys.platform != 'win32': return.

FunctionWindowsmacOSWhat the student feels
enable_password_manager WebView2's IsPasswordAutosaveEnabled switched on, so the institution password can be saved and filled. Nothing. WKWebView has no equivalent for a non-browser app. Types a full institutional password on every sign-in.
persist_session_cookies The app's own "stay signed in", re-dating session cookies in place. Nothing. At an institution whose identity provider offers no "stay signed in", re-authenticates every launch.
_clear_profile_identity_data ClearBrowsingDataAsync, the only API that reaches saved passwords and autofill. Returns False. clear_cookies() still runs and is in fact broader (all website data types), but the saved-password half is unreached. Logout may leave saved identity data behind.

Four structural differences, already read out of pywebview

  • storage_path is ignored on macOS. cocoa.py always uses WKWebsiteDataStore.defaultDataStore(); only private_mode matters. So the webview/ folder is empty there and the real profile lives in ~/Library/WebKit/<bundle id>. The "Web view profile" line dev.py prints is a Windows truth.
  • get_cookies() scopes differently. macOS filters by substring of the URL the window was opened with; Windows scopes to the current URL. Same answer for Canvas, but a sibling host whose domain is a substring of the login URL would be included on macOS only.
  • clear_cookies() is fire-and-forget on macOS (AppHelper.callAfter, completion handler ignored) against a synchronous Invoke on Windows. So "log out and quit immediately" is verified on Windows and cannot be verified from here.
  • Google SSO is the open risk. Google's embedded-webview policy names WKWebView explicitly and does not name WebView2 - which is exactly why Windows measured working with no change at all. A Google-SSO institution may therefore be blocked on macOS while working on Windows.

Do not "fix" a macOS block by spoofing the user agent. pywebview's user_agent is a webview.start() parameter, so it is process-global and would apply to the main window too - and it would be deliberate circumvention of a provider's security control. Detect and report instead.

The order to work in, when a Mac is available

  1. Drive the extension route end to end. Expected to pass, and it is the cheap win. If it does, macOS has a complete zero-typing sign-in on day one.
  2. Drive the app's own window against a SAML or CAS institution, then a Google one. The second is the one that might be blocked, and it must be measured rather than assumed in either direction.
  3. Then decide whether the window's three missing pieces are worth building WKWebView equivalents for, or whether macOS should lead with the extension and the token. That is a product call, and it should be made with the measurements in hand rather than before them.
