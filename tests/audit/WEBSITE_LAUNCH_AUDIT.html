This is the strongest indie-app trust story I have read in a while — the disclaimer and privacy pages are genuinely better than most commercial equivalents. What is not ready is the part a student actually touches: a homepage that weighs 64 MB, a macOS system requirement the build cannot honour, and a broken overlay that traps phone users on a black screen.

B1 FixedBlocker

The macOS requirement you advertise is not the one you ship

The site states three different minimums, and the most generous one is very likely wrong. The build declares LSMinimumSystemVersion 11.0, but the actual floor is set by whatever native wheels pip resolves at build time — and the CI runner is macos-14. The transcription stack's arm64 wheels are tagged for macOS 14. A student on Ventura downloads 151 MB and gets a failure.

Measured schema.org "macOS 12 or later"
hero + cards "macOS 11 Big Sur or later"
mac-setup "Monterey, Ventura, Sonoma, Sequoia, Tahoe all work"
spec LSMinimumSystemVersion 11.0

PyPI arm64 wheel floors — onnxruntime macosx_14_0 only, av 14.0, numpy 11.0 + 14.0
CI runner macos-14 (pip prefers the highest compatible tag)
requirements onnxruntime and numpy are unpinned transitives

macOS versions ever tested (tests/audit/*.md): 15 and 26 only
branch fix/macos13-transcription-wheels — not merged into main

The deeper problem is that an unpinned native transitive means the macOS floor changes silently on every rebuild. The v2.0.1 DMG from July may well run on Big Sur; a rebuild today may not, and nothing would tell you.

Fix
  • Pick one number and use it in all four places. Until someone runs the DMG on an older Mac, the defensible claim is macOS 14 Sonoma or later.
  • Pin onnxruntime and numpy explicitly in requirements.txt so the floor stops drifting, or merge fix/macos13-transcription-wheels.
  • Drop "Monterey, Ventura, Sonoma, Sequoia, Tahoe all work" — you have evidence for two of those five. Replace with the versions you have actually run.

Outcome: Fixed — macOS 14 stated in all four places; spec floor raised to 14.0; CI now measures the real floor from the built binaries and fails if it drifts.

B2 FixedBlocker

The homepage costs 64 MB to read, and GitHub Pages is already refusing requests

Four demo videos autoplay with no poster and no lazy-loading, and every one buffers to completion. The hero is a 4.8 MB square PNG rendered into a 327px slot on a phone; your avatar is a 2 MB image rendered at 72px. During a plain page load the server dropped an icon with a 503.

Measured — live site, real browser Sync_Review_Demo.mp4 26,637 KB readyState 4 (fully buffered)
Quick_Sync_Demo.mp4 14,276 KB readyState 4
AI-Optimization.mp4 13,048 KB readyState 4
DownloadAllCourses_Folders.mp4 2,652 KB readyState 4
images 8,860 KB
total ≈ 64 MB · 36 requests · docs/assets total 87 MB

CanvasDownloaderHero.png natural 2048×2048 → rendered 327×327 (4,822 KB)
icon_website_brk.png natural 2048×2048 → rendered 72px (2,101 KB)

console: 503 on assets/icon_conv_excel.png — an icon silently failed to render

Resource Timing reports only 11.5 MB, which is why this is easy to miss: the three large videos arrive by range request and report transferSize: 300. The Content-Length figures above are the truth.

Fix
  • Give every video a poster, drop autoplay, add preload="none", and play on click or on intersection. This alone removes ~55 MB from a normal visit.
  • Re-encode the four MP4s — they are screen recordings, so a 1280px-wide H.264 at CRF 28 typically lands 5–10× smaller. 26 MB for one UI clip is roughly 20× what it needs.
  • Export the hero at 1200px and the avatar at 220px, as WebP. That is ~6.9 MB → under 150 KB.
  • Add loading="lazy" and decoding="async" to the icon images.

Outcome: Fixed — videos re-encoded 2560px→1920px (still autoplaying MP4), hero and avatar to WebP. 64 MB → 5.0 MB, verified in-browser.

B3 PartlyBlocker

Version, release and download are three different answers

version.py says 2.0.2. The newest release is v2.0.1. The site's structured data says 2.0.1, and both download buttons resolve to the v2.0.1 assets. That is internally consistent only if you are launching 2.0.1. If 2.0.2 is the launch build, there is no release to serve it — and no macOS DMG at all, because the mac workflow uploads a CI artifact with 14-day retention rather than attaching an asset to a release.

Measured version.py 2.0.2
git tags v1.0.0, v2.0.0, v2.0.1 (no v2.0.2)
index.html softwareVersion 2.0.1

Releases API — v2.0.1 Canvas_Downloader_v2.0.1_Windows.exe 140,130,279 B (9 downloads)
                   v2.0.1 Canvas_Downloader_v2.0.1_MacOS.dmg 151,503,877 B (8 downloads)
build-macos.yml — workflow_dispatch, upload-artifact, retention 14 days

v2.0.0 is flagged prerelease and holds a file named ..._v2.0.1_macOS.dmg

There is also a latent trap in the resolver on index.html, thanks-win.html and thanks-mac.html: it skips draft releases but not prerelease, and takes the first match in API order. Publish a beta and every visitor is silently served the beta.

Fix
  • Decide the launch version, then make all three agree. If it is 2.0.2: cut the tag, run the mac workflow, and attach the DMG to the release — the download buttons read release assets, not artifacts.
  • Add if (rel.prerelease) continue; next to the existing draft check in all three resolvers.
  • Rename the mislabelled asset on v2.0.0, or delete that prerelease.

Outcome: Partly — prerelease guard added to all three resolvers and the site now says 2.0.2. You still need to cut the v2.0.2 release and attach the DMG.

H1 FixedHigh

Clicking a screenshot on the homepage opens a black dead end

The video-modal markup, CSS and script are all present twice. Two elements share id="videoModal" and two share id="modalVideo", so getElementById always returns the first — while #modalImage lives in the second. Clicking the Today-mode screenshot therefore writes the image into the hidden modal and opens the empty one. The visible X then does nothing, because one script toggles .show and the other .active.

Reproduced on the live site document.querySelectorAll('[id="videoModal"]').length 2
document.querySelectorAll('[id="modalVideo"]').length 2
getElementById('videoModal') → modal index 0
#modalImage lives in modal index 1

after clicking .expandable-img (TodayMode_Auto-download-new-files.png):
  modal 0 — class "video-modal active", visible true, contains visible image false
  modal 1 — hidden, opacity 0, holds the image

clicking the visible X → class unchanged, closedByX: false
pressing Escape → closedByEscape: true

On desktop a user presses Escape and moves on. On a phone there is no Escape key, so the only way out is tapping the backdrop precisely — otherwise the homepage is a black screen.

Fix
  • Delete the first modal block and its script (index.html ~4689–4725) and keep the second, which is the one that handles both video and image. Then correct the ids so the surviving script resolves its own elements.
  • Remove the now-dead .video-modal.show CSS block so only one rule set governs the modal.
  • Add a visible close affordance that works on touch.

Outcome: Fixed — duplicate modal, script and stylesheet removed. Image opens, X closes, video expand still works, Escape still works.

H2 FixedHigh

On a phone there is no download button until you scroll past the fold

The hero image consumes the entire first screen, pushing the first download control just below the fold. The nav's Download button collapses to a bare icon with no label. And OS detection is a single navigator.platform test with a Windows fallback — so every phone, tablet and Chromebook is offered a Windows .exe, and every iPad (which reports MacIntel) is offered a macOS DMG it cannot install.

Measured at 390×844 viewport height 844 px
first download CTA top 886 px → 1.05 screens down
nav Download button label hidden (innerText empty, icon only)
navigator.platform on mobile "Win32" → Windows card shown
page height 14,224 px
Fix
  • On viewports under ~700px, move the download control above the hero image, or cap the image height so both fit.
  • Keep the word "Download" in the nav button on mobile — an unlabelled icon is the weakest possible CTA.
  • Detect touch/mobile explicitly and swap in a third state: "Canvas Downloader is a desktop app for Windows and Mac" plus a copy-link / email-to-myself action. Right now a shared link — the main way this spreads between students — lands on the wrong offer.
  • Replace navigator.platform (deprecated) with navigator.userAgentData?.platform falling back to a UA test.

Outcome: Fixed — CTA moved above the artwork (886px → 507px, above the fold), nav keeps its label, and a phone/tablet state replaces the uninstallable download.

H3 FixedHigh

The macOS guide explains a permission using behaviour you deliberately removed

Step 5 lists System Events as dialog 3 of 6 and explains it as: "keeps Office windows hidden during conversions — nothing flashes or bounces in the Dock." That behaviour was measured as counter-productive and deleted on 2026-08-10. The permission is still real — but for a different reason, and it does not appear where the page says it does.

Cross-checked against engine/applescript_bridge.py set visible of … to false removed — measured: no hide is quietest (visible 0/7 samples vs 2/11 with it)

remaining System Events use — 4 sites, all exists process
  lines 1765, 1942, 2020, 2169 — the Office quit / teardown path

first_run_permission_setup primes _APP_TRIPLES only (Word/Excel/PowerPoint)
→ the System Events prompt fires at end of the conversion phase, not in the opening batch

So two statements on that page are wrong: the reason for the permission, and the promise that the app "asks macOS for all remaining permissions up front — so they never interrupt a run later." If the user walks away, that prompt goes unanswered and Office is left open with the Recents list unpurged — exactly the symptom the teardown exists to prevent.

Same drift exists inside the app. TCC_FIRST_RUN_NOTICE ends with "you are only asked once", which is false on macOS 15+ where the App Data consent is per-session. Your website is currently more accurate than your app on this point.

Fix
  • Rewrite dialog 3's explanation: System Events lets the app check whether Word, Excel or PowerPoint is still running, so it can close the copies it opened and clean up your Recent Files list.
  • Say when it appears — at the end of the first conversion run, not in the opening batch — or prime it in first_run_permission_setup so the page becomes true as written.
  • Amend TCC_FIRST_RUN_NOTICE: only asked once, except the macOS 15+ App Data prompt, which returns once per session unless Full Disk Access is granted.

Outcome: Fixed in both — guide rewritten and moved to position 6, wizard row corrected, and TCC_FIRST_RUN_NOTICE in the app fixed with two new tests.

H4 FixedHigh

Every download depends on an unauthenticated API call, and the failure state lies

Both platforms resolve their download by calling the GitHub API from the browser. That endpoint is rate-limited to 60 requests per hour per IP — and a university NAT is one IP. When it fails, thanks-mac.html still renders the headline "Your download has started! 🎉" while nothing has downloaded.

Read from the page source index.html, thanks-win.html, thanks-mac.html →
  fetch('https://api.github.com/repos/.../releases?per_page=30')
unauthenticated limit: 60 req/hour/IP (shared campus NAT = one IP)

on failure — mac: headline still reads "Your download has started! 🎉",
  only recovery is a link reading "Download didn't start? Click here"
on failure — win: button falls back to releases.html, which makes the same call
Fix
  • Only show the success headline after the fetch resolves. Until then, render a neutral "Preparing your download…", and on failure switch to "We couldn't start the download — get it from GitHub Releases" with a prominent button.
  • Ship a hardcoded fallback URL for the current release so a rate-limited visitor still gets a working direct link rather than a page that makes the same failing call.

Outcome: Fixed — the headline only claims success once the download resolves, and a failure switches to a working GitHub button.

The homepage FAQ promotes the same feature with none of that, and the neighbouring FAQ answers the legality question in a way the disclaimer would not endorse.

The two pages, side by side disclaimer.html — "Canvas Downloader does not read that setting… Saving a recording may be contrary to your institution's IT rules or to Panopto's terms of service"

Outcome: Fixed — both FAQ answers now carry the caveat and link the disclaimer.

What is already strong

keep these

Listed because they are the reason the fixes above are worth doing — the foundation is good.

The disclaimer

Honest about exactly the thing most projects hide: that the app ignores Panopto's download flag. Naming the risk, explaining why the feature exists, and inviting rights holders to make contact is a stronger legal position than silence.

The privacy policy

Specific, structured, and it names each third party with the condition that triggers it. Better than most commercial software. Only the website's own third parties are missing (M1).

The security Q&A

"The certificate program isn't a safety check — it's a publisher registry" is the correct argument, made without defensiveness. Pointing at three specific files to read is a real verification path, not a gesture.

The macOS wizard

Version-branched instructions, real screenshots of every dialog, and a troubleshooting section organised by what the user did wrong. This is the hardest onboarding on either platform and it is handled thoroughly.

The positioning

"Built by a student, between lectures" with a real name, face and university is the right trust play for an unsigned app, and the problem framing — hours lost, exam-season chaos, manual AI prep — is specific to the audience rather than generic.
