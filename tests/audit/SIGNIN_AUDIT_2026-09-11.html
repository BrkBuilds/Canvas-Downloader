Canvas Sign-In Audit

Browser-session login, audited against the access-token path it has to replace. Driven against real CBS Canvas, the real engine and the real app window.

date 2026-09-11

The credential design is sound and the security boundary holds. The cookie reaches the Canvas host and nothing else, downloads work, the app restores and logs out correctly. All of that is now measured against real Canvas rather than mocks.

One blocker: Panopto cannot work on a browser session as the code stands. Canvas requires an access token to mint a sessionless launch, so every Panopto path 403s. A working replacement route exists and was proven end to end during this audit.

Second theme: friction. A first sign-in shows a spinner for ~15 s after the login page is already loaded, and a second click throws the window away and starts the wait again.

Blocker

Blocker
F-01

Panopto is dead on a browser session — Canvas requires a token to mint a launch

panopto/auth.py · panopto/discovery.py · panopto/runner.py · panopto/stream.py · sync/analysis.py

Every Panopto path in the app starts at sessionless_launch. Canvas refuses that endpoint outright unless the request carries an access token — this is Canvas' own code, not a permission quirk of one course:

# canvas-lms app/controllers/lti/concerns/sessionless_launches.rb
def generate_session_token
  # only allow from API, and not from files domain
  raise UnauthorizedClient unless @access_token

Measured on your account: all 36 Panopto items of course 43660, both URL forms the app builds, every one 403 "user not authorised to perform that action", while users/self and the Files API on the same session return 200. So a browser-mode user gets no recordings, no transcripts and no subtitles — reported as per-recording failures, not as an explanation.

A working route exists, and it is proven. Students watch these lectures in a browser, so the in-app launch works. Starting the app's own LTI form chain at the module-item page, with the Canvas credential on its domain-scoped jar: 
/courses/43660/modules/items/1087340
  → /api/lti/authorize
  → cbs.cloud.panopto.eu/Panopto/Pages/Embed.aspx
  delivery id b58f9a14-…  ·  Panopto cookies .ASPXAUTH, csrfToken, sandboxCookie
  DeliveryInfo OK — duration 1115 s, 2 streams
  Canvas cookies leaked to Panopto: none
The change is contained: build the in-app URL when the credential is a browser session and attach the credential to the first hop. discover_course_videos already has the module item id it needs.

F-02

Seven credential sites are pinned by no test at all

panopto/runner.py ×3 · panopto/stream.py · sync/analysis.py · core/canvas_logic.py ×2

The census test bans a hand-written Bearer {…} header. It does not notice a site reverting to cm.api_key, which is '' in browser mode — the exact shape this repo keeps hitting. I wrote eight such mutants and ran them against every related test file:

SURVIVED  panopto runner discovery reverts to cm.api_key
SURVIVED  panopto runner auth bootstrap
SURVIVED  panopto per-task credential
SURVIVED  panopto duration probe
SURVIVED  sync analysis Panopto discovery
SURVIVED  per-worker module client from api_key
SURVIVED  page-metadata client from api_key
CAUGHT    download engine session built from a bearer      ← the only guarded one
Fix. An AST census that fails on any new site passing .api_key into a credential-consuming call (lti_launch, discover_course_videos, _CanvasREST, _new_canvas_client) — the same instrument the repo already uses for the mkdir and delete-gate families.
Major
F-03

First sign-in: 15 s of spinner over a login page that was ready in 3

core/browser_login.py — SILENT_TIMEOUT

Both modes start hidden on the same 15 s clock. Measured in the real app against real CBS:

 1.3 s  notice: "Checking your Canvas sign-in"
 3.3 s  hidden window is already sitting on the CBS Entra login page
17.0 s  window finally shown   → 13.7 s of dead time

The 15 s is a constant, so a faster laptop makes the gap larger, not smaller. It is paid by exactly the people who must log in by hand — first run, and every re-login after the SSO session lapses.

Options. Show the window as soon as the page has settled on a non-Canvas host (the IdP), which is the moment a human is needed; or keep a fixed clock but cut it to ~4 s for interactive attempts; or show immediately on click and accept a brief flash when the silent path would have won.
Major
F-04

Clicking "Sign in with Canvas" twice destroys the open window

ui/auth.py:begin_browser_signin → browser_login.reset()

The window is not modal and has no owner, so it can end up behind the main window. The natural response is to click the button again. Measured:

0.2 s  window open, notice "Finish signing in to Canvas"
2.5 s  window destroyed, notice back to "Checking your Canvas sign-in"
17.6 s window returns — CBS login reloaded, anything typed is gone
Fix. If a job for the same address is already needs_user, re-show and focus that window instead of resetting. Cheap, and it removes a 15 s punishment for a reasonable action.
Major
F-05

When a browser session expires, the app tells the user to paste a token

ui/course_selector.py:2271,2273 · shared/components.py:226,228,1864 · ui/auth.py reauth header

All four force_reauth call sites hard-code token wording — "Please reconnect with a new token" — and the reconnect screen adds "Generate a fresh access token (guide below) and paste it here - that's the only thing that changed." At a school that has turned token creation off, that instruction cannot be followed at all.

Worse, force_reauth deletes the stored browser credential, so the silent renewal that would have fixed the session in a few seconds never runs. refresh_silently() exists in core/browser_login.py and has no callers.

Fix. Route a browser-mode expiry to a hidden renewal first, and only fall back to the login screen — with sign-in-shaped copy — if that fails. This is the single biggest lever on "I don't want to re-login too often".
Major
F-06

A stuck WebView2 from a previous launch can now stop the app starting

start.py — private_mode=False + storage_path

Before this feature every launch got its own temp profile, so a leftover WebView2 could not affect the next start. Now both windows share one folder. Simulated the documented MSIX shutdown hang (freeze the WebView2 processes, kill the host), then launched again — twice, same result:

control (no wedge)   B loads in 5.4 s
wedged orphan        B waits 45 s → WebView2 init fails, E_ABORT (0x80004004)
                     → the app's own window never loads

An ordinary hard kill is fine — I measured 0 surviving WebView2 processes — so this needs the specific wedge case. But the orphan reaper runs inside _boot, racing the main window's WebView2 init, so it is not a reliable defence.

Fix. Reap before webview.start(), and treat "a live msedgewebview2 holding our profile folder whose host process is gone" as proof of ownership — the profile path is unique to this app.
Major
F-07

The credential does not fit Windows Credential Manager — it always lands in a file

ui/auth.py:store_browser_credential → store_token → _save_fallback_token

Measured with your real session through the app's own writer:

payload 1,630 chars = 3,260 bytes   (CredWrite limit 2,560)
CredWrite → error 1783 "The stub received bad data"
stored instead in .token_fallback (DPAPI)      load-back: usable, verify OK

cookie sizes:  canvas_session 762 · cf_clearance 426 · _csrf_token 102 · log_session_id 32

It works — store_token's fallback-and-verify design absorbs it — but three things are now untrue: browser-login.md says the login is stored "in the SAME OS credential store as a token"; privacy.html and index.html tell users their credential is in Credential Manager / Keychain; and on macOS there is no fallback by design, so a Keychain refusal there means signing in again every launch.

Fix. Harvest only what authenticates: canvas_session alone verified fine against real Canvas. Dropping the other three puts the payload near 1,800 bytes — inside the limit, in the OS store, and a smaller secret at rest. Otherwise keep the fallback and correct the rule file and the website.

Minor
F-08

The sign-in poll hits the Canvas API up to ~1,200 times while the user types

core/browser_login.py:_worker

At any institution without SSO the window sits on the Canvas host, and Canvas hands an anonymous visitor a session cookie — measured: GET /login/canvas returns Set-Cookie: canvas_session=…; httponly. So _harvest succeeds and verify() fires on every 0.5 s poll, for up to the 10-minute interactive window.

Fix. Skip verify() when the session cookie value is unchanged since the last failed check. Canvas rotates it on login, so the successful attempt still fires immediately.
Minor
F-09

macOS parity: four real differences, none of them verified on a Mac

webview/platforms/cocoa.py (pywebview 6.1)

  • storage_path is ignored on macOS — the Cocoa backend always uses WKWebsiteDataStore.defaultDataStore(). The webview/ folder start.py creates is empty there, and the gitignore comment describing it as the profile is Windows-only.
  • get_cookies() filters by substring of the URL the window was opened with (if domain not in self.url), where Windows scopes to the current URL. Same answer for Canvas; different mechanism, and a sibling host whose name is a substring would be included.
  • clear_cookies() is fire-and-forget (AppHelper.callAfter, completion handler ignored) and removes all website data types. Windows' wipe is synchronous and cookie-only. Logout-then-quit is verified on Windows, unverifiable here.
  • show() calls activateIgnoringOtherApps_ on macOS; Windows calls Activate(), which under focus-stealing prevention may only flash the taskbar — so the sign-in window can stay behind the app.
Minor
F-10

No password autofill in the sign-in window, and it is one flag on Windows

WebView2 CoreWebView2Settings

Read off the live control: IsPasswordAutosaveEnabled = false, IsGeneralAutofillEnabled = true. So the window never offers to save a password and never fills one — every re-login is typed in full. On Windows this is settable; on macOS WKWebView has no equivalent for a non-browser app, and passkeys need entitlements an ad-hoc-signed bundle cannot carry. Also from the same read: AreDefaultContextMenusEnabled = false (no right-click paste) and AreBrowserAcceleratorKeysEnabled = false (no Back, no reload) — both tied to pywebview's debug flag.

Minor
F-11

Exported pages lose their file links in session mode

Canvas adds verifier= to file URLs only for token requests (files_handler.rb:56, attachment.rb:110 — a session request is in_app). Measured on real Canvas: 0 of 5 file URLs carried a verifier. Downloads are unaffected (the cookie authenticates the first hop — proven above), but images and links inside exported HTML/Markdown pages now need the reader to be logged into Canvas in whatever browser opens them.

Minor
F-12

Smaller items

  • .token_fallback is not gitignored — and this feature makes it the primary store on Windows. A dev run writes a credential blob into the repo root.
  • User-Agent capture is unreliable — evaluate_js returned None in 2 of 3 real runs (the bridge is re-injected per navigation). Harmless: measured that Canvas accepts the python-requests UA and Cloudflare did not challenge. Reading CoreWebView2.Settings.UserAgent would be deterministic.
  • Cookies for an IP-address Canvas are silently dropped by aiohttp.CookieJar (unsafe=False); requests drops them for a dotless host like localhost. Only self-hosted-by-IP setups.
  • A two-session hot loop is reachable in theory: with browser_login_pending set and the job reset elsewhere, the poll fragment reruns the app and adopt_pending_browser_login returns without clearing the flag. Needs two live sessions; reasoned, not reproduced.
  • test_the_course_cache_really_accepts_a_browser_credential is vacuous — it builds a local dict and never touches core.course_cache, though its docstring claims the opposite.
  • health_log's docstring is now false — it says pywebview "hands it a fresh temp folder every launch", which the persistent profile ends. The reaper still works.
  • A UTF-8 BOM in the settings file silently discards every saved setting and the saved login (json.load with encoding='utf-8'). Pre-existing; utf-8-sig reads both. I hit this by accident writing a config from PowerShell.

Evidence: real CBS Canvas (account 424242), real engine, real app window over WebView2's debugging port. Offline probes used purpose-built local servers with positive controls — one early result (cookies surviving logout) was an artifact of a fake IdP re-setting cookies on /favicon.ico and is withdrawn.

The session cookies used for this audit are a complete login and appear in the session transcript. Sign out of Canvas in that browser to invalidate them.
